# pi.dev + DeepSeek: краткое руководство по работе с агентом в терминале

**Что здесь описано.** pi — ИИ-агент, который работает в терминале: читает файлы, выполняет команды
и сам правит код по вашим указаниям. DeepSeek — семейство моделей, на которых он работает.

**Для кого:** человек, который впервые открывает pi и хочет не кликать наугад, а понимать, как всё устроено.
**Результат:** от первого запуска до собственных расширений, субагентов (агентов-помощников) и
осознанной траты токенов (единиц текста, по которым тарифицируются запросы к модели — подробнее в разделе 6).

**Как читать.** Части I–III — обязательный путь новичка; в каждой части есть задание «сделай сам».
Часть IV — когда базовый цикл «план → код → ревью → шип (сдача)» уже не вызывает вопросов. Приложения —
не для чтения подряд: инвентарь конкретного проекта, журнал чисел и типичных ошибок, перенос опыта в
новые проекты.

**Достоверность.** Цены моделей сверены с локальным каталогом pi (`models-store.json`), цифры стоимости —
пересчитаны командой `pi-cost` по реальным сессиям (2026-10-15). Всё, что относится к «нашему проекту»,
живёт в этом репозитории.

# Часть I. Первый запуск

## 1. Установка и проверка

**Цель:** pi запускается, видит DeepSeek и умеет выполнять shell-команды. Без этого всё остальное не работает.

### 1.1 Git Bash — обязателен на Windows

pi на Windows выполняет команды агента через Git Bash. Без него агент не может запустить ни одной
команды — только читать и писать файлы.

```text
1. Установи Git for Windows: https://git-scm.com/download/win
2. В pi введи:  !printf 'Bash works\n'
3. Если не подхватилось — в ~/.pi/agent/settings.json:
   "shellPath": "C:\\Program Files\\Git\\bin\\bash.exe"   (путь — по месту установки)
```

### 1.2 Ключ DeepSeek

Ключ живёт в переменной окружения `DEEPSEEK_API_KEY` (или настраивается через `/login deepseek`).
Проверь оба пункта:

```bash
pi auth check --provider deepseek --json
pi --list-models deepseek
```

Должны быть видны модели `deepseek-flash` и `deepseek-v4-pro`.

### 1.3 Первый запуск в папке проекта

При первом запуске в новой папке pi спрашивает **доверие (trust)**: проектные ресурсы (`.pi/`,
`AGENTS.md`) загружаются только после подтверждения. Подтверди, затем `/reload`.

> Задание: пройди шаги 1.1–1.3 и покажи `pi auth check` с обеими моделями.

## 2. Экран, стоп, навигация, сессии

Если ты пришёл из чисто агентных IDE, например Cursor, ZCode — главное, что нужно перестроить в голове: **здесь нет
кнопок, есть клавиши.** Всё, что в GUI было кнопкой или выпадающим списком, в pi — хоткей или slash-команда.

### 2.1 Экран: три зоны

| Зона в pi                 | Что это                                    | Аналог в GUI  |
| ------------------------- | ------------------------------------------ | ------------- |
| Транскрипт (лента сверху) | промпты, ответы, tool calls, вывод         | чат-панель    |
| Редактор (строка внизу)   | сюда набираешь промпт                      | поле ввода    |
| Футер (status bar)        | папка, сессия, модель, контекст, стоимость | статус-строка |

Текст в редакторе **не отправляется**, пока не нажмёшь `Enter`. Пока не нажал — можно менять модель,
уровень мышления, редактировать текст, прикладывать файлы (`@`).

### 2.2 Стоп! Как остановить агента

Кнопка «Stop» из GUI — это клавиша **`Escape`**:

- **`Escape`** — прервать текущий прогон: агент остановится, сообщения вернутся в редактор.
- `Ctrl+C` — это **НЕ «копировать»** (см. 2.6). Первое нажатие очищает редактор, второе — выходит из pi.
- `Ctrl+D` — выйти из pi (когда редактор пуст).

Пока агент работает, можно не только останавливать, но и управлять:

| Что хочешь                              | Клавиша (Windows)      | Смысл                                           |
| --------------------------------------- | ---------------------- | ----------------------------------------------- |
| Подправить задачу во время выполнения   | набрал текст → `Enter` | steering: встанет после текущего хода           |
| Добавить работу после текущей задачи    | `Ctrl+Q`               | follow-up: выполнится, когда текущая закончится |
| Вернуть отложенные сообщения в редактор | `Alt+Q`                | dequeue                                         |
| Остановить совсем                       | `Escape`               | abort                                           |

### 2.3 Навигация по транскрипту

В fullscreen-режиме скроллом владеет pi: листать удобнее клавишами, но колесо мыши тоже работает.

| Действие                                           | Клавиша (Windows)                                                |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| Прокрутка на страницу                              | `PageUp` / `PageDown`                                            |
| **Вниз + следовать за новым выводом (автоскролл)** | **`Ctrl+End`**                                                   |
| В самое начало                                     | `Ctrl+Home`                                                      |
| К предыдущему/следующему сообщению                 | `Ctrl+Up` / `Ctrl+Down`                                          |
| Поиск по транскрипту                               | `Ctrl+F` (`Enter` — след., `Shift+Enter` — пред., `Esc` — выйти) |
| Развернуть/свернуть вывод инструмента              | `Ctrl+O`                                                         |
| Свернуть/развернуть thinking                       | `Ctrl+T`                                                         |

**`Ctrl+End` — основная клавиша:** после любой прокрутки вверх она возвращает вниз и снова «следит»
за работой агента. `Ctrl+Up`/`Ctrl+Down` — перемещение между пользовательскими запросами.

### 2.4 Смена модели, не удаляя набранный текст

Модель и уровень мышления меняются **поверх** набранного промпта — текст в редакторе остаётся.

- **`Ctrl+L`** — селектор модели (выпадающий список, как в GUI). Выбрал → `Enter`, промпт сохраняется.
- **`Ctrl+P` / `Alt+P`** — следующая / предыдущая модель в цикле.
- **`Shift+Tab`** — цикл уровня мышления.
- `/model` и `/thinking` — то же самое через slash-команды.

Состав цикла настраивается через `/scoped-models`. Текущая модель видна в футере.

### 2.5 Клавиши редактора промпта

Редактор промпта работает как readline/emacs: навигация и правка — на клавиатуре. Выделения и «выделить
всё» в редакторе нет, поэтому «выделить и удалить» здесь не работает: чтобы стереть весь ввод, нажми
`Ctrl+C` один раз (второе нажатие выходит из pi, см. 2.2), а слова удаляй по одному — `Ctrl+W` назад,
`Alt+D` вперёд. Мышь работает для выделения и копирования текста и для прокрутки, но не для правки.
Основное:

| Клавиша                                        | Действие                                                      |
| ---------------------------------------------- | ------------------------------------------------------------- |
| `Ctrl+A` / `Ctrl+E`                            | в начало / в конец строки                                     |
| `Ctrl+Left` / `Ctrl+Right` (`Alt+B` / `Alt+F`) | по слову влево/вправо                                         |
| `Ctrl+W` / `Alt+Backspace`                     | удалить слово назад                                           |
| `Alt+D` / `Alt+Delete`                         | удалить слово вперёд                                          |
| `Ctrl+K` / `Ctrl+U`                            | удалить до конца / до начала строки                           |
| `Ctrl+C`                                       | очистить весь ввод (первое нажатие; второе — выйти из pi)     |
| `Ctrl+Y`                                       | вставить удалённое (yank)                                     |
| `Ctrl+Z`                                       | отмена                                                        |
| `Up` / `Down`                                  | история промптов (курсор в начале строки)                     |
| `Shift+Enter` / `Ctrl+J`                       | новая строка без отправки                                     |
| `Tab`                                          | автодополнение пути                                           |
| `@` + текст                                    | поиск и прикрепление файла к промпту                          |
| `Ctrl+G`                                       | открыть промпт во внешнем редакторе (Zed) для длинного текста |

`Enter` = отправить. Многострочный промпт — `Shift+Enter` (или `Ctrl+G` → Zed).

### 2.6 Копирование и вставка — не перепутай `Ctrl+C`

- **`Ctrl+X`** — скопировать последний ответ ассистента (внутри pi).
- Выделение текста терминала — `Ctrl+Shift+C` / `Ctrl+Shift+V` (Windows Terminal) или мышью с `Shift`.
- Вставка изображения/файла в промпт — `Alt+V`.

### 2.7 Shell-команды прямо из pi

Не нужно выходить из pi и открывать второй терминал:

- `!git status` — выполнить команду, **вывод уйдёт модели** (она его увидит).
- `!!git status` — выполнить, **вывод модели не отправляется** (только для себя).

Правило: **`!!` для больших выводов** (например, `!!git diff`) — смотришь сам, агент не расходует токены.

### 2.8 Сессии — это чаты

«Чат» в pi называется **сессией**. Одна сессия = один JSONL-файл в `~/.pi/agent/sessions/`, привязанный
к рабочей папке. Постоянной боковой панели нет — список **открывается командой** `/resume`.

| Задача (как в GUI)                     | Команда / клавиша              | Пояснение                                             |
| -------------------------------------- | ------------------------------ | ----------------------------------------------------- |
| **Новый чат**                          | `/new`                         | новая пустая сессия в той же папке                    |
| Продолжить последний чат               | `pi --continue`                | при запуске из терминала                              |
| **Список чатов / история**             | `/resume`                      | интерактивный селектор; печатай — фильтруется         |
| Переключиться на чат                   | `Enter` в `/resume`            | выбрать из списка                                     |
| Переключиться по id                    | `pi --session <id>`            | id виден в `/session`                                 |
| Переименовать чат                      | `/name Мой-чат`                | или `Ctrl+R` в `/resume`                              |
| Удалить чат                            | `Ctrl+D` в `/resume`           | `Ctrl+Backspace` — без подтверждения, если поиск пуст |
| Инфо о чате (id, токены, стоимость)    | `/session`                     | смотри после каждой задачи                            |
| Сортировка / пути / только именованные | `Ctrl+S` / `Ctrl+P` / `Ctrl+N` | внутри `/resume`                                      |
| Импортировать сессию                   | `/import <path>`               | перенос чата из другого места                         |

Осторожно: внутри `/resume` клавиши `Ctrl+P` и `Ctrl+D` значат **не то же**, что в редакторе.

**Ветки — то, чего нет в Cursor.** Сессия — это **дерево**, а не линейный чат. Можно вернуться к любой
реплике и пойти другим путём, не теряя старую ветку:

| Действие                                       | Команда  | Когда                               |
| ---------------------------------------------- | -------- | ----------------------------------- |
| Прыгнуть к более ранней реплике в том же файле | `/tree`  | альтернативы должны остаться вместе |
| Сделать из реплики отдельный чат               | `/fork`  | альтернатива — независимая работа   |
| Скопировать текущую ветку в новый чат          | `/clone` | нужна отдельная копия состояния     |

Сжатие и экспорт: `/compact` — сжать контекст; `/export` / `/share` / `/copy` — сохранить или поделиться
чатом. Одноразовый чат (не сохраняется): `pi --no-session`.

### 2.9 Два режима интерфейса

- **Fullscreen** (по умолчанию): pi владеет экраном, скролл — клавишами (`End`, `PageUp/Down`).
- **Regular** (`/settings` → tui mode, или `--tui-mode regular`): скролл и мышь отданы терминалу,
  выделение мышью и `Ctrl+Shift+C`/`V` работают как обычно.

Многие начинают в regular, потом переходят в fullscreen ради `Ctrl+End`/`Ctrl+O`/поиска.

### 2.10 Шпаргалка-переводчик Cursor/Zed → pi

| В GUI (Cursor/Zed)                 | В pi (терминал)                                 |
| ---------------------------------- | ----------------------------------------------- |
| Кнопка Stop                        | `Escape`                                        |
| Выпадающий список моделей          | `Ctrl+L` (меню) или `Ctrl+P`/`Alt+P` (цикл)     |
| Переключатель уровня мышления      | `Shift+Tab`                                     |
| Поле ввода чата                    | редактор внизу, `Enter` = отправить             |
| Многострочный ввод                 | `Shift+Enter` / `Ctrl+J` / `Ctrl+G` (Zed)       |
| Боковая панель с чатами / историей | `/resume` (список + поиск)                      |
| Новый чат                          | `/new`                                          |
| Переименовать чат                  | `/name` (`Ctrl+R` в списке)                     |
| Ветки одного чата                  | `/tree`, `/fork`, `/clone`                      |
| Терминальная вкладка               | `!команда` / `!!команда`                        |
| Accept/Apply изменения             | агент правит файлы сам — смотри diff (раздел 9) |
| Список всех шорткатов              | `/hotkeys`                                      |

**Запомни три вещи:** `Escape` = стоп · `Ctrl+End` = вниз и следить · `Ctrl+L` = сменить модель, не удаляя промпт.

### 3.3 CLI (главное)

```bash
pi                                   # interactive TUI
pi --print "..."                     # одноразовый запуск
pi --mode json "..." > events.jsonl  # структурированные события
pi --mode rpc                        # управление процессом
pi --continue / --resume / --session <id> / --fork <id> / --no-session
pi --model deepseek/deepseek-flash --thinking low   # выбор модели+уровня
pi --models "deepseek/*"           # сузить стартовый выбор и цикл моделей
pi --list-models deepseek           # каталог моделей с фильтром
pi --tools read,bash,edit,write,codemode  # набор инструментов
pi -e ./ext.ts --skill ./skill --prompt-template ./p.md
pi --append-system-prompt ./rules.md --system-prompt ./sys.md
pi --tui-mode regular --offline
pi install <src> / pi remove <src> / pi update [--all|--models] / pi list / pi config
pi auth check --provider deepseek --json
pi mcp add|remove|list|login|logout
```

# Часть II. Как это устроено

## 4. Ментальная модель pi

**pi — минимальный расширяемый агент для терминала.** Главная идея: «подстрой pi под свой рабочий
процесс, а не наоборот». Всё, что в Cursor «встроено», здесь собирается из маленьких примитивов.

### 4.1 Цикл агента

```
сообщение пользователя → запрос = системный промпт + активная ветка истории
                        + описания инструментов + настройки модели
→ поток ответа модели (текст + tool calls)
→ pi выполняет каждый tool call и записывает результат
→ если нужен следующий шаг (tool results / очередь сообщений) → новый ход
→ иначе — конец прогона
```

- **Steering** (`Enter`) — сообщение встаёт после текущего хода и корректирует задачу.
- **Follow-up** (`Alt+Enter` / на Windows `Ctrl+Q`) — сообщение ждёт завершения текущей задачи.
- **Abort** (`Escape`) — останавливает прогон, сообщения возвращаются в редактор.

### 4.2 Контекст

- Строится из **активной ветки** сессии + системного промпта + описаний инструментов + описаний skills.
- Системный промпт = базовые инструкции pi + найденные контекст-файлы (`AGENTS.md`, `CLAUDE.md`,
  `AGENTS.override.md`).
- **Skills** анонсируются именем и описанием, полные инструкции грузятся **по требованию**.
- Расширения могут добавлять инструкции или трансформировать контекст.

### 4.3 Сессии — это дерево

- Сессия = JSONL-файл; сообщения и события образуют **дерево**; путь по дереву = **ветка (branch)**.
- Активная ветка даёт историю для следующего запроса.
- **Компакция** вставляет summary-запись, заменяющую старые сообщения в последующих запросах (оригинал
  остаётся в дереве).
- Продолжить с ранней точки = новая ветка в том же файле. Продолжение сессии (resume) **сохраняет префикс → кэш-хиты**.

### 4.4 Пять интерфейсов

| Режим             | Как                               | Для чего                                 |
| ----------------- | --------------------------------- | ---------------------------------------- |
| Interactive (TUI) | `pi`                              | ежедневная работа                        |
| Print             | `pi --print "..."`                | одноразовые/скриптовые задачи, пайплайны |
| JSON event stream | `pi --mode json "..."`            | потребление структурированных событий    |
| RPC               | `pi --mode rpc`                   | управление отдельным процессом pi        |
| TypeScript SDK    | `@earendil-works/pi-coding-agent` | встраивание агента в приложение          |

Все режимы используют один и тот же агент и механизм сессий.

### 4.5 Расширения и ресурсы

| Ресурс                      | Что делает                                                            |
| --------------------------- | --------------------------------------------------------------------- |
| **Extension** (`.ts`)       | исполняемое поведение: инструменты, команды, провайдеры, события, TUI |
| **Skill** (`SKILL.md`)      | инструкции + файлы, грузятся по требованию                            |
| **Prompt template** (`.md`) | переиспользуемый текст → `/команда`                                   |
| **Theme**                   | цвета терминала                                                       |
| **Pi package**              | npm/git-дистрибутив набора ресурсов                                   |

### 4.6 Доверие и права

- Проектный `.pi/` загружается **только после trust** (pi спрашивает при первом запуске в папке).
- Инструменты работают с правами процесса pi — **песочницы нет**. Не доверяй чужим репозиториям и расширениям.
- `--approve` / `--no-approve` — принудительный trust на один запуск.

## 5. Настройки: settings.json

### 5.1 Актуальный конфиг этого компьютера

`~/.pi/agent/settings.json` (глобально, pi 1.1.0):

```jsonc
{
  "theme": "dark",
  "defaultModel": "deepseek-flash", // основная модель
  "defaultThinkingLevel": "low", // reasoning-бюджет по умолчанию
  "showCacheMissNotices": true, // видеть промахи кэша
  "defaultTools": [
    "+bash",
    "+grep",
    "+find",
    "+ls",
    "+codemode",
    "+tool_search",
  ],
}
```

- Записи `+name` в `defaultTools` — **аддитивные**: добавляются к набору по умолчанию `read, bash, edit, write`.
  Итоговый набор: read, bash, edit, write, grep, find, ls, codemode, tool_search. Имя без `+` — заменяет весь набор.
- `defaultThinkingLevel: "low"` (значение pi по умолчанию — `"medium"`) — экономия reasoning-токенов.
- Проектный `.pi/settings.json` переопределяет пользовательский (в этом репо — доп. инструменты +
  `hideThinkingBlock`).
- `/settings` — TUI-редактор частых опций; `pi config` — интерактивный TUI по ресурсам (для CI не годится).

### 5.2 Полезные ключи по группам (полный список — `docs/settings.md`)

- **Модель/мышление:** `defaultProvider`, `defaultModel`, `defaultThinkingLevel`, `modelThinkingLevels`,
  `thinkingBudgets`, `enabledModels` (паттерны для стартового выбора и Ctrl+P-цикла), `hideThinkingBlock`,
  `showCacheMissNotices`, `cacheWarming` (`off|streaming|idle`).
- **Инструменты:** `defaultTools`, `codemode.mode`, `codemode.inlineBudget`.
- **Компакция:** `compaction.enabled`, `compaction.reserveTokens` (16384), `compaction.keepRecentTokens`
  (20000), `compaction.modelOverrides`, `branchSummary.reserveTokens`.
- **Терминал:** `tuiMode` (`fullscreen|regular`), `fullscreenWheelScrollLines`, `fullscreenCopyOnSelect`,
  `fullscreenScrollbar`, `theme`, `quietStartup`.
- **Сеть/повторы (retry):** `transport`, `retry.enabled`, `retry.maxRetries` (3), `retry.provider.maxRetries`
  (0 — оставь 0: квоты и лимиты тогда обрабатывает сам pi), `httpProxy`.
- **Shell:** `shellPath`, `shellCommandPrefix`, `npmCommand`.
- **Ресурсы:** `extensions`, `skills`, `prompts`, `themes`, `packages`, `enableSkillCommands`.

### 5.3 DeepSeek + cacheWarming

`cacheWarming` (прогрев кэша в простое/потоке) работает только для моделей с объявленным `promptCache`
(время жизни кэша в секундах) и только когда pi оценивает экономию от избегаемого промаха хотя бы в
$0.05. У DeepSeek-моделей в каталоге `promptCache` нет — подогрев по умолчанию не активен.
Сам автокэш DeepSeek работает и без этого. Если захочешь включить — задай консервативный TTL через
`modelOverrides` в `models.json` (см. `docs/models.md`), но сначала проверь реальный TTL кэша DeepSeek
в их документации.

## 6. Модели и деньги: DeepSeek, цены, кэш

### 6.1 Две модели (цены сверены с каталогом pi, `models-store.json`)

|                                     | `deepseek-flash` (V4.1 Flash) | `deepseek-v4-pro` (V4 Pro) |
| ----------------------------------- | ----------------------------- | -------------------------- |
| Input (промах кэша)                 | **$0.30 / 1M**                | $1.32 / 1M                 |
| Input (попадание кэша, `cacheRead`) | **$0.006 / 1M** (×50 дешевле) | $0.044 / 1M (×30 дешевле)  |
| Output                              | **$1.20 / 1M**                | $3.96 / 1M                 |
| Запись в кэш (`cacheWrite`)         | **$0**                        | $0                         |
| Контекст / max output               | 1M / 384k                     | 1M / 384k                  |
| Вход                                | текст + **изображения**       | только текст               |
| Уровни мышления                     | `low` / `high` / `max`        | только `high` / `max`      |

> Цены таблицы — из каталога pi и совпадают с **пиковыми** тарифами DeepSeek. В непиковые часы
> (всё, кроме 01:00–04:00 и 06:00–10:00 UTC, пн–пт, кроме госпраздников Китая) DeepSeek берёт ровно
> вдвое меньше: у flash промах кэша $0.15 / попадание $0.003 / output $0.6, у pro — $0.66 / $0.022 / $1.98.

Провайдер `deepseek`, base URL `https://api.deepseek.com`, API `openai-completions`.

### 6.2 Механика кэша — главный экономический рычаг

- DeepSeek кэширует **префикс запроса на своей стороне автоматически** — никаких маркеров не нужно.
- **Запись в кэш бесплатна** (`cacheWrite = 0`) — отдельной платы за запись DeepSeek не берёт.
- Попадание в кэш в **30–50 раз дешевле** промаха. Главное правило экономии: **сохраняй стабильный префикс** (системный
  промпт + AGENTS.md + набор инструментов + история) и не переключай модель/инструменты посреди задачи.
- Reasoning-токены **остаются в контексте** (`requiresReasoningContentOnAssistantMessages: true`) — они
  пересылаются как часть истории и тарифицируются как output.

### 6.3 Три вывода

1. **Кэш-промах vs попадание = ×30–50.** Стабильный префикс — твой главный актив.
2. **Output (включая reasoning) дороже input в 3–4 раза.** Проси краткие ответы, держи уровень мышления на `low`.
3. **flash в ~4.4× дешевле pro по input и в 3.3× по output** и при этом мультимодальная → основная рабочая модель.

### 6.4 Имена моделей: flash/v4-pro vs chat/reasoner

Каталог pi называет модели `deepseek-flash` (DeepSeek V4.1 Flash) и `deepseek-v4-pro` (DeepSeek V4 Pro) —
эти ID использует pi. Классические ID публичного API DeepSeek — `deepseek-chat` и `deepseek-reasoner`;
в Zed на этой машине они перечислены в `available_models`, а `default_model` настроен на `deepseek-flash`.
Какие ID принимает твой ключ — смотри в `api-docs.deepseek.com`; каталог pi обновляется командой
`pi update --models`.

## 7. Экономия токенов

### 7.1 Десять правил

1. **Контекст — единица стоимости.** Сначала `find`/`grep`/`ls`, потом `read` только нужных диапазонов
   (`offset`/`limit`). Никогда не выгружай в контекст репозиторий целиком.
2. **Локальность кэша.** Не меняй модель/уровень мышления/набор инструментов в середине задачи — каждый switch =
   промах кэша = ×30–50 по вводу на следующем запросе.
3. **Распределение задач по моделям.** `flash` для 90% токенов, `pro` — только для архитектуры/отладки/безопасности.
4. **Бюджет reasoning.** `low` по умолчанию. Reasoning = output-токены, дорогие и накапливаются в контексте.
5. **Компакция.** Окно в 1M токенов — не склад. `/compact` при разрастании; короткая история = дешёвый префикс.
6. **Фильтруй вывод инструментов.** `codemode` режет/агрегирует результат до попадания в контекст.
7. **Параллель вместо последовательности.** Каждый round-trip пересылает весь контекст. Один `codemode`
   с 5 параллельными чтениями лучше 5 последовательных шагов.
8. **Измеряй, а не верь.** Футер (usage/cost), `/session`, `showCacheMissNotices`.
9. **Fork/continue вместо рестарта.** Продолжение сохраняет префикс → кэш-хиты с первого запроса.
10. **Точечные правки.** `edit` с маленьким `oldText` вместо перезаписи файла целиком.

### 7.2 Инструменты измерения

- **Футер TUI** — накопленный usage и cost за сессию; с расширением `deepseek-balance` (установлено в этом
  проекте) под ним виден живой баланс аккаунта DeepSeek, `/balance` — повторная синхронизация с сервером.
- **`/session`** — файл, число сообщений, токены, стоимость текущей сессии.
- **`tools/pi-cost/pi-cost.mjs`** — агрегат по всем сессиям `~/.pi/agent/sessions`:
  `node tools/pi-cost/pi-cost.mjs [paths...] [flags]`; `--today`, `--last N`, `--top N`, `--json`.
  Считает все ветки (реальный расход), cache-hit = `cacheRead / (input + cacheRead)`.
  `--health` — поведенческий gate: FAIL (exit 1), если v4-pro > 80% стоимости (flash должен быть рабочей
  моделью по умолчанию); WARN при v4-pro > 50% или cache-hit < 90%. Подробности — § 16.1.
- **`https://platform.deepseek.com/usage`** — расход аккаунта целиком (разбор — раздел 7.5).

### 7.3 Баланс DeepSeek в футере

Расширение `deepseek-balance` (`.pi/extensions/deepseek-balance.ts`, в этом репо и в global) добавляет
под встроенный футер строку с текущим балансом:

```text
deepseek $46.44 left · this session -$0.149
```

**Как работает:**

- При старте сессии один раз запрашивает реальный баланс с `https://api.deepseek.com/user/balance`.
  Ключ берётся из провайдера pi (`ctx.modelRegistry.getApiKeyForProvider("deepseek")`) — ничего не хардкодится.
- Между запросами вычитает траты текущей сессии (usage-записи из `ctx.sessionManager.getEntries()`),
  поэтому цифра обновляется в реальном времени после каждого ответа модели.
- **`/balance`** — принудительная повторная синхронизация с сервером (нужно, если тратил деньги из другого приложения
  или параллельной сессии).
- Ошибки показываются как есть: `deepseek balance: HTTP 401` / `no DeepSeek API key (auth.json / DEEPSEEK_API_KEY)`.
- Не путай с встроенной строкой `5.0%/1.0M (auto)` в футере — это рабочая память (заполненность контекста),
  а не деньги.

**Установка:**

```bash
mkdir -p ~/.pi/agent/extensions
cp .pi/extensions/deepseek-balance.ts ~/.pi/agent/extensions/   # из корня этого репозитория
# в pi: /reload — в футере появится «deepseek $… left»
```

Нет локальной копии репо — файл можно взять с GitHub:
`https://github.com/lightclove/Zed_and_Pi.dev/raw/main/.pi/extensions/deepseek-balance.ts`

**Ключевые API кода:** `ctx.ui.setStatus(key, text)` — своя строка статуса в TUI; события
`session_start` / `message_end` / `session_compact` — точки обновления; `registerCommand("balance")` —
слаш-команда. Полный код — раздел 15 (инвентарь) и файл `.pi/extensions/deepseek-balance.ts`.

### 7.5 Расход на платформе DeepSeek: как читать метрики

Страница **Usage** на `platform.deepseek.com` показывает расход по тем же метрикам, что API возвращает в
блоке `usage` каждого ответа, — только агрегированно и по всему аккаунту. Наши инструменты (`pi-cost`,
футер, `/balance`) меряют те же величины, но по вашим сессиям. Ниже — глоссарий её терминов, как читать
цифры и что с ними делать. (Страница открывается под логином; термины и метрики ниже — по официальной
документации DeepSeek.)

**Глоссарий**

| Термин | Простыми словами | Зачем смотреть |
|---|---|---|
| **Токен** | «Кусочек текста» и единица оплаты. Ориентир: ~0.3 токена на английский символ, ~0.6 на китайский; точное число приходит в блоке `usage` ответа | Всё считается в токенах |
| **Input (prompt) tokens** | Сколько токенов ушло на вход: запрос + история + описания инструментов | Растёт с историей → чистить компакцией |
| **Output (completion) tokens** | Сколько модель сгенерировала в ответ | Дороже входа в 3–4 раза → просить кратко |
| **Reasoning tokens** | «Размышления» модели (thinking); входят в output и тарифицируются как output | На рутине держать уровень мышления низким |
| **Cache hit tokens** (`prompt_cache_hit_tokens`) | Часть входа, взятая из кэша DeepSeek (дёшево) | Чем больше — тем дешевле |
| **Cache miss tokens** (`prompt_cache_miss_tokens`) | Часть входа, обработанная заново (дорого) | Чем меньше — тем лучше |
| **Cache-hit rate (hit%)** | Доля входа из кэша: `cacheRead / (input + cacheRead)` | Главный показатель экономии |
| **Context length** | Сколько токенов помещается в один запрос (у наших моделей 1M) | Переполнение → компакция |
| **Max output** | Предел токенов в ответе (384K) | Большой предел провоцирует длинные ответы |
| **Peak / off-peak** | Тариф по времени: в пик дороже, в off-peak ровно вдвое дешевле | Тяжёлые прогоны выгоднее в off-peak |
| **Balance** | Деньги на аккаунте: `total = granted + topped_up`; сначала тратятся подарочные (`granted`) | Следить за остатком |
| **Cost** | Списано за период, в валюте аккаунта (CNY или USD) | Итог, к которому сводится всё остальное |

**Как читать цифры (что с чем сравнивать)**

- **Input против output.** Output (включая reasoning) дороже входа в 3–4 раза. Большой output = длинные
  ответы или высокий уровень мышления.
- **Cache hit против miss.** Высокая доля hit (у нас ~96%) = стабильный префикс и дешёвый вход. Падение
  hit — сигнал, что вы сменили модель/инструменты посреди задачи или оборвали историю.
- **По моделям.** `deepseek-v4-pro` дороже `deepseek-flash` (input ×4.4, output ×3.3): если основную
  стоимость даёт pro — рутину вернуть на flash.
- **По времени.** Off-peak (всё, кроме 01:00–04:00 и 06:00–10:00 UTC, пн–пт, кроме госпраздников
  Китая) вдвое дешевле; длинные автономные прогоны логично ставить туда.
- **Баланс.** Это не расход за период, а «сколько ещё можно потратить».

**Как применять в проекте**

| Что хотите узнать | Где смотреть |
|---|---|
| Остаток денег на аккаунте | футер (расширение `deepseek-balance`) или `/balance` |
| Расход и hit% за N дней | `node tools/pi-cost/pi-cost.mjs --last 7` |
| Стоимость текущей сессии | футер (usage/cost) или `/session` |
| Общий расход аккаунта | страница Usage на `platform.deepseek.com` |

Что делать по этим числам:

- hit% падает → не переключать модель/инструменты в середине задачи (липкий роутер, раздел 11.3);
- output и reasoning растут → опустить уровень мышления (`/thinking low`);
- pro даёт основную стоимость → держать рутину на flash (раздел 7.1);
- нужен длинный автономный прогон → планировать на off-peak.

[Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing),

# Часть III. Ежедневная работа

## 8. Рабочий цикл: план → код → ревью → шип

```
/plan            → спланировать (flash, low): цель, дизайн, чеклист, риски
реализация       → код (flash, low), точечные edit, дешёвые проверки (typecheck/один тест)
/review          → ревью проиндексированных (staged) изменений (или delegate-субагент-ревьюер)
исправления      → по findings
полный прогон    → тесты + lint + build
/ship            → прод-чеклист: проверки, тесты, docs, commit message
коммит           → git, ревью диффа в Zed
```

Шаблоны `/plan`, `/review`, `/ship` — в `.pi/prompts/` этого репозитория (см. Приложение 15); при переносе
в другие проекты их стоит положить в `~/.pi/agent/prompts/` (раздел 17).
Каждый содержит гейты: `/plan` — допущения, дешёвые проверки, альтернативы; `/review` — findings с
`file:line`, severity и вердиктом ship/fix/block; `/ship` — numbers gate (тесты/типчек/стоимость) и
финальный sanity-проход.

Параллельная версия (много независимых модулей):

```bash
pi --model deepseek/deepseek-flash --print "спланируй модуль A" > plan-a.md &
pi --model deepseek/deepseek-flash --print "спланируй модуль B" > plan-b.md &
wait
```

**Принципы, лежащие в основе** (полный свод — skill `engineering-principles`): лови ошибки на самой ранней
стадии, дешёвая проверка раньше дорогой, контракт до кода, числа вместо мнений, YAGNI. Они заложены в
AGENTS.md, промпты и расширения этого проекта.

## 9. Диффы: что именно изменил агент

**Главное отличие от Cursor:** pi пишет изменения в файлы **сразу**, кнопки Accept/Reject нет. Значит,
«понять, что изменил агент» = посмотреть **дифф**. Четыре уровня:

**1) Дифф прямо в pi (в транскрипте).** Каждый вызов `edit` рисуется цветным диффом: красный `-` —
удалённые строки, зелёный `+` — добавленные, подсветка внутри строки — изменённые слова, тусклые строки —
контекст. `Ctrl+O` — развернуть/свернуть вывод инструмента. Инструмент `write` (новый файл) показывает
содержимое целиком. `edit` требует точный `oldText`: не нашёл — правка не применится, и ничего лишнего агент
не перепишет.

**2) Дифф через git — эталон.** Не выходя из pi:

- `!git status` — что изменено/добавлено/удалено (вывод уйдёт модели).
- `!!git diff` — полный дифф, модели не отправляется (не расходует токены).
- `!!git diff --stat` — только файлы и число строк. `!!git diff -- src/foo.ts` — по одному файлу.
- `!!git diff --staged` — что уже в индексе.

**3) Ревью в Zed.** Git panel (`Ctrl+Shift+G`) — список изменённых файлов, выбор файла открывает дифф;
gutter — цветные метки изменённых строк; `editor: toggle git blame` — кто и когда менял строку.

**4) Accept/Reject средствами git.**

- Принять по кускам: `git add -p` (интерактивно, **в терминале**, не через `!`).
- Откатить файл: `git restore <file>` (или `git checkout -- <file>`).
- Спрятать всё: `git stash`. Закоммитить: `git add` + `git commit`.

Перед коммитом — `git status`, коммить явными путями (см. раздел 16.3). Для ревью проиндексированных
(staged) изменений: сначала `git add -p`, потом `/review`.

| Cursor                   | pi / Zed                                      |
| ------------------------ | --------------------------------------------- |
| Inline before/after      | дифф в транскрипте pi, `Ctrl+O`               |
| Accept / Reject          | `git add -p` / `git restore <file>`           |
| Панель изменённых файлов | git panel Zed (`Ctrl+Shift+G`) / `git status` |
| «Кто менял строку»       | gutter + `editor: toggle git blame`           |
| Стадия + коммит          | `git add -p` → `git commit`                   |

## 10. Zed рядом: редактор и git-клиент

**Роли:** Zed = быстрый редактор + git-клиент, pi = оркестратор в терминале (координирует работу). Не требуй от Zed оркестрации;
не редактируй длинный текст в однострочном редакторе pi.

### 10.1 Конфиг: где что лежит

- Глобально: `%APPDATA%\Zed\` (`settings.json`, `keymap.json`, `tasks.json`).
- Проектно: `.zed/settings.json` в корне репо (перекрывает global для этого проекта; создаётся через
  `zed: open project settings`).
- Открыть руками не искать: `zed: open settings`, `zed: open keymap`, `zed: open tasks`.
- `keymap.json` — **массив** объектов `[{ "context": "...", "bindings": {...} }]`.
- Zed-агент (Agent Panel) держи на дешёвой модели — на этой машине `default_model: deepseek-flash`.

### 10.2 Что выучить в первую очередь

- **Multi-buffer:** `Ctrl+Shift+F` (поиск по проекту) → результат — редактируемый буфер (массовый rename).
- **Vim mode:** `"vim_mode": true` в settings. **Мультикурсор** (`Alt+Click`, `Ctrl+D`), split-панели, outline.
- **Git:** `Ctrl+Shift+G` (git panel), gutter-метки, `editor: toggle git blame`.
- **Терминал:** `` Ctrl+` `` — запускай `pi` прямо там.
- **Связка с pi:** `"externalEditor": "zed --wait"` в `~/.pi/agent/settings.json` → `Ctrl+G` в pi откроет

### 10.3 Терминал Zed: проброс клавиш в pi

В терминале Zed `Shift+Enter`, `Ctrl+-`, `Ctrl+Alt+]` не доходят до pi как надо. Чинится `keymap.json`:

```jsonc
[
  {
    "context": "Terminal",
    "bindings": {
      "shift-enter": ["terminal::SendText", "\u001b[13;2u"],
      "ctrl--": ["terminal::SendText", "\u001b[45;5u"],

  },

```

Zed подхватывает keymap автоматически; `zed: reload keymap` — если нет.

### 10.4 LSP: `.zed/settings.json` (настроено в этом проекте)

Zed сам определяет и скачивает language servers; проектный конфиг нужен, чтобы **зафиксировать** серверы,
включить inlay hints и выровнять форматирование (файл в корне, заготовка — `templates/zed-lsp/`).

```jsonc
// .zed/settings.json
{
  "format_on_save": "on",
  "languages": {
    "TypeScript": { "language_servers": ["vtsls", "..."], "tab_size": 2 },
    "JavaScript": { "language_servers": ["vtsls", "..."], "tab_size": 2 },
  },
  "inlay_hints": { "enabled": true, "show_type_hints": true },
}
```

- **`vtsls`** — TS/JS-сервер Zed по умолчанию (скачивается сам, без npm); `"..."` оставляет остальные серверы по умолчанию,
  `"!name"` — исключает. Per-server настройки — под top-level `"lsp": { "<server>": {...} }`.
- **Inlay hints** выключены по умолчанию — включаются здесь или глобально.
- **Хоткеи LSP** уже есть из `base_keymap: VSCode`: `F12` определение, `Shift+Alt+F12` ссылки, `F2` rename,
  `Ctrl+.` code actions.
- **Python/Rust/SQL** — готовые закомментированные блоки в `templates/zed-lsp/settings.json` (Python:
  `basedpyright`+`ruff`, нужен python-рантайм/uv; Rust: `rust-analyzer`, нужен rustup; SQL: только
  `sql-formatter` — **встроенного SQL-сервера нет**; семантика — через Postgres MCP, раздел 13.7).
- **Не всё работает на проектном уровне** (theme/vim_mode/base_keymap — только global).

### 10.5 Сессии vs вкладки: новый чат и новая вкладка

В pi **вкладок нет** — есть **сессии**. Два действия:

| Хочу                                       | Как                 | Где настройка                                                        |
| ------------------------------------------ | ------------------- | -------------------------------------------------------------------- |
| Новый чат в текущей вкладке (новая сессия) | `/new` или **`F2`** | `~/.pi/agent/keybindings.json`: `"app.session.new": ["f2", "alt+n"]` |
| Новый чат в новой вкладке (параллельный)   | **`Ctrl+Shift+N`**  | Zed: задача `pi` + `task::Spawn`                                     |

Задача Zed (`%APPDATA%\Zed\tasks.json`, глобальная — работает во всех проектах):

```jsonc
[
  {
    "label": "pi",
    "command": "pi",
    "use_new_terminal": true,
    "allow_concurrent_runs": true,
    "reveal": "always",
  },
]
```

Биндинг (`%APPDATA%\Zed\keymap.json`) — перекрывает стандартный `ctrl-shift-n` (New Window/Open Recent):

```jsonc
{
  "context": "Workspace",
  "bindings": { "ctrl-shift-n": ["task::Spawn", { "task_name": "pi" }] },
}
```

- `task::Spawn` работает и когда фокус в терминале; `command` резолвится в `pi.cmd` (проверено `where pi`);
  `cwd` задачи — корень проекта.
- Встроенные вкладки терминала Zed: `ctrl-n` (в фокусе терминала) или `ctrl-shift-`` — новый терминал;
`ctrl-pageup`/`ctrl-pagedown`— переключение;`ctrl-shift-w` — закрыть.
- **Почему `alt+n` не сработал:** в Zed-терминале он свободен, но на Windows его, вероятно, перехватывает
  меню приложения — опирайся на `F2` (F-клавиши в Terminal-контексте свободны).
- Reload: pi — `/reload`; Zed подхватывает `tasks.json`/`keymap.json` сам.

# Часть IV. Продвинутый уровень

## 11. Оркестрация: от одного агента к команде

В pi **нет встроенных субагентов** как в Cursor — из коробки оркестрация собирается из примитивов, плюс
официальный пример-расширение `subagent` (установлено) и проектное `delegate`. Правило выбора:
**начни с наименее мощного механизма, которого достаточно.**

### 11.1 Что когда использовать

| Нужно                                        | Примитив                            | Где                                |
| -------------------------------------------- | ----------------------------------- | ---------------------------------- |
| Постоянные инструкции для папки              | `AGENTS.md`                         | корень проекта / `~/.pi/agent/`    |
| Переиспользуемый промпт из `/`               | Prompt template                     | `.pi/prompts/*.md`                 |
| Инструкции + файлы под тип задачи            | Skill                               | `.pi/skills/*/SKILL.md`            |
| Маршрутизация запросов между моделями        | Virtual model                       | extension `registerVirtualModel`   |
| Исполняемый инструмент/команда/событие       | Extension                           | `.pi/extensions/*.ts`              |
| Изолированные субагенты (как в Cursor)       | Extension `subagent` (офиц. пример) | `~/.pi/agent/extensions/subagent/` |
| Параллельные tool-вызовы + фильтрация вывода | codemode                            | встроенный (`+codemode`)           |
| Внешние инструменты (GitHub, БД, docs)       | MCP server                          | `mcp.json`                         |
| Дистрибутив набора ресурсов                  | Pi package                          | `pi install`                       |

### 11.2 Пять уровней

- **Уровень 0 — один агент + распределение моделей по уровням.** Один «мозг», адаптивная стоимость: виртуальная модель
  `deepseek/auto` сама выбирает `flash`/`pro`. Выгода: кэш-локальность, без ручного переключения.
- **Уровень 1 — специалисты на запрос.** Skills и шаблоны (`/plan`, `/review`, `/ship`, `code-review`)
  дают экспертизу только когда нужно — без постоянной платы за контекст.
- **Уровень 2 — изолированные субагенты.** Инструмент `subagent` (отдельный процесс pi; режимы
  single/parallel/chain) и проектное `delegate` (вложенный DeepSeek-вызов). Оба изолируют контекст:
  параллельная независимая работа (research/review/plan) не загрязняет главный контекст.
- **Уровень 3 — исполняемые агенты.** Extension-инструменты могут вызывать другие инструменты
  (`ctx.executeTool`) и делать вложенные LLM-вызовы (`ctx.modelRegistry.streamSimple`). Это и есть
  «агент как код».
- **Уровень 4 — процессная оркестрация.** Несколько `pi --print`/`--mode json`/RPC/SDK-процессов
  параллельно — пайплайны, CI, многомодульная разработка.

### 11.3 Роутер `deepseek/auto`

Пользователь выбирает одну модель `deepseek/auto`, а роутер решает физическую модель на каждый запрос
(`low` → flash, `high`/`max` → v4-pro). Три правила маршрутизации:

1. **Липкая маршрутизация (sticky routing).** Продолжения и повторы (retry) остаются на той же модели — иначе каждый tool-шаг = промах кэша.
   Кэш-локальность важнее «оптимального» выбора на каждом шаге.
2. **Изоляция контекста через делегирование.** Независимая работа — в субагенте с собственным промптом,
   результат возвращается одной строкой. Так главный контекст не раздувается.
3. **Состояние через дерево сессии.** Роутер хранит фазу в `state` (следует за веткой, переживает
   компакцию); расширения хранят данные в `details` tool-результатов или `appendEntry`.

Использование: `/model deepseek/auto`, эскалация — `/thinking` (или `Shift+Tab`). Код — раздел 12.6.

### 11.4 Субагенты

**`subagent`** (официальный пример-расширение, установлен): модель сама вызывает его из обычного промпта:

- `Use scout to find all authentication code` — один агент;
- `Run 2 scouts in parallel: one for models, one for providers` — параллельно;
- `Use a chain: scout finds X, then planner suggests Y` — цепочка (`{previous}` передаёт вывод предыдущего шага).

Режимы: single `{agent, task}`, parallel `{tasks: [...]}` (**макс. 8 задач, 4 одновременно**),
chain `{chain: [...]}`. Каждый субагент = **отдельный процесс pi с изолированным контекстом**; в выводе —
turns/токены/кэш/`$cost`/model по каждому агенту. `Ctrl+C` убивает дочерние процессы.

Агент = markdown-файл с YAML-шапкой (пользовательские — `~/.pi/agent/agents/*.md`, проектные —
`.pi/agents/*.md`, включаются через `agentScope: "project" | "both"`):

```markdown
---
name: reviewer
description: Code review specialist
tools: read, grep, find, ls, bash
model: deepseek/deepseek-v4-pro
---

Системный промпт агента...
```

Поля: `name`, `description`, `tools`, `model` (формат `provider/id`; нет — наследует модель и уровень
мышления родительской сессии). Агенты перечитываются при каждом вызове — правки без рестарта. Установка и
адаптация под DeepSeek — раздел 16.2. Workflow-пресеты: `/implement` (scout→planner→worker),
`/scout-and-plan`, `/implement-and-review` (промпт-шаблоны `~/.pi/agent/prompts/*.md`).

**`delegate`** (проектное расширение): то же самое, но одним вложенным вызовом DeepSeek внутри процесса
pi — быстрее и дешевле, чем отдельный процесс. Код — раздел 12.7.

### 11.5 Принципы

- **События вместо опроса (polling).** `pi.on(...)` (agent/tool/session/message события) для реакций и гейтов.
- **Параллельность через codemode / процессы.** Независимые чтения и greps — в `Promise.allSettled`;
  независимые задачи — в параллельные `pi --print`.
- **Экспертная эскалация.** Классификаторы (`models.classify`) могут выбирать модель по сложности задачи
  без ручного вмешательства (пример — `jev-router.ts` в `examples/extensions/`).

## 12. Свои расширения: API и эталонный код

Расширение — TypeScript-модуль с default-фабрикой `(pi: ExtensionAPI) => void`. Pi использует `jiti`,
компиляция не нужна. Файлы: `~/.pi/agent/extensions/` (глобально) или `.pi/extensions/` (проект).

### 12.1 ExtensionAPI — главные методы

| Метод                                                          | Назначение                               |
| -------------------------------------------------------------- | ---------------------------------------- |
| `pi.registerTool(tool)`                                        | LLM-вызываемый инструмент (`defineTool`) |
| `pi.registerCommand(name, {description, handler})`             | `/команда`                               |
| `pi.registerShortcut(key, {handler})` / `pi.registerFlag(...)` | шорткаты / CLI-флаги                     |
| `pi.registerProvider(...)` / `pi.registerMcpServer(...)`       | свой провайдер / MCP-сервер              |
| `pi.registerVirtualModel({...})`                               | виртуальная модель-роутер                |
| `pi.on(event, handler)`                                        | подписка на события                      |
| `pi.sendMessage(...)` / `pi.sendUserMessage(...)`              | сообщения агенту из кода                 |
| `pi.appendEntry(customType, data)`                             | долговечное состояние вне контекста      |
| `pi.getActiveTools()` / `pi.setActiveTools([...])`             | управление активными инструментами       |
| `pi.getSettings()` / `pi.getCommands()`                        | настройки / команды                      |
| `pi.exec(cmd, args)`                                           | shell из расширения                      |
| `pi.setModel(...)` / `pi.setThinkingLevel(...)`                | смена модели/мышления                    |

### 12.2 События (выборочно)

`project_trust`, `session_start/_shutdown/_tree`, `session_before_compact/_fork/_switch`,
`agent_start/_end/_before_settle/_settled`, `turn_start/_end`, `message_start/_update/_end`,
`tool_call` (можно блокировать/мутировать), `tool_result` (можно редактировать),
`tool_execution_start/_update/_end`, `context` / `context_with_system` (трансформация контекста),
`before_provider_request/_headers`, `after_provider_response`, `provider_stream_event`,
`model_select`, `thinking_level_select`, `user_bash`, `input`.

Паттерн permission-gate (подтверждать опасные вызовы) — через `tool_call` + `pi.getAllTools()` annotations
(`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`).

### 12.3 Контексты и ModelRegistry

- **ExtensionContext** (события): `ui`, `mode`, `cwd`, `sessionManager`, `modelRegistry`, `model`,
  `scopedModels`, `thinkingLevel`, `isIdle()`, `isProjectTrusted()`, `signal`, `abort()`,
  `getContextUsage()`, `compact()`, `getSystemPrompt()`.
- **ExtensionToolContext** (execute инструмента) = + `tools` + `executeTool(name, args, opts)` (вложенные
  tool-вызовы, не попадают в транскрипт, учитываются в `nestedCalls`).
- **ExtensionCommandContext** (команды) = + `waitForIdle()`, `newSession()`, `fork()`, `navigateTree()`,
  `switchSession()`, `reload()`, `getSystemPromptOptions()`.

```ts
ctx.modelRegistry.find(provider, id)                       // модель по id
ctx.modelRegistry.findOfType("classifier", p, id)          // классификатор
ctx.modelRegistry.complete(model, context, options?)       // Promise<AssistantMessage>
ctx.modelRegistry.streamSimple(model, context, options?)   // AssistantMessageEventStream (+ .result())
ctx.modelRegistry.classify(model, {state, questions})      // классификация
ctx.modelRegistry.generateImages(model, {input})           // генерация изображений
ctx.modelRegistry.registerVirtualModel(def)                // регистрация роутера
```

`Context` = `{ systemPrompt?, messages: Message[], tools? }`; `Message` имеет `role` и `timestamp`.

### 12.4 Виртуальная модель: поля `route(request, ctx)`

| Поле `request`           | Значение                                                        |
| ------------------------ | --------------------------------------------------------------- |
| `model`, `thinkingLevel` | выбранная виртуальная модель и уровень                          |
| `reason`                 | `user` / `continuation` / `retry` / `direct`                    |
| `previous`               | физическая модель+уровень последнего успешного ответа           |
| `failed`                 | для `retry`: физическая модель+уровень+message упавшего запроса |
| `state`                  | состояние роутера на ветке (JSON, переживает компакцию)         |
| `messages`               | конверсация запроса                                             |
| `signal`                 | abort-сигнал                                                    |

Возврат: `{ model, thinkingLevel, state? }`. Нельзя роутить на другую виртуальную модель.

### 12.5 Codemode (JS-скрипты)

Включение: `"defaultTools": ["+codemode"]`. Модель пишет JS, который вызывает инструменты и не-LLM модели;
в контекст попадает только вывод скрипта. Глобальные: `tools.<name>(args)` (parallel-safe), `text()`,
`image()`, `console.log()`, `return`, `exit()`, `store(key,value)`/`load(key)`, `ALL_TOOLS`,
`searchTools(query)`, `describeTool(name)`, `describeNamespace(name)`, `models.*`.

```js
// @options: {"max_output_tokens": 2000, "timeout_ms": 60000}
const [a, b, c] = await Promise.allSettled([
  tools.grep({ pattern: "TODO" }),
  tools.find({ pattern: "**/*.spec.ts" }),
  tools.read({ path: "src/main.ts", offset: 1, limit: 200 }),
]);
return [a, b, c].map((r) => (r.status === "fulfilled" ? r.value : "ERR"));
```

`bash` в скриптах возвращает `{ output, truncated, full_output_path?, exit_code, wall_time_seconds }`.
Лимиты: 256MB памяти, `max_output_tokens` 10000 по умолчанию, нет Node/файловой системы/сети/таймеров.

### 12.6 Эталонный код 1: роутер (`.pi/extensions/deepseek-router.ts`)

```ts
import type {
  ExtensionAPI,
  ExtensionContext,
  ModelRoute,
  ModelRouteRequest,
} from "@earendil-works/pi-coding-agent";

const PROVIDER = "deepseek";
const FLASH = "deepseek-flash";
const PRO = "deepseek-v4-pro";

function routeTo(
  request: ModelRouteRequest,
  ctx: ExtensionContext,
  id: string,
  level: string,
): ModelRoute {
  const model = ctx.modelRegistry.find(PROVIDER, id);
  if (!model) throw new Error(`Model ${PROVIDER}/${id} is not in the catalog`);
  return { model, thinkingLevel: level };
}

export default function (pi: ExtensionAPI) {
  pi.registerVirtualModel({
    provider: PROVIDER,
    id: "auto",
    name: "Auto (flash ↔ pro)",
    thinkingLevels: ["low", "high", "max"],
    contextWindow: 1_000_000,
    maxTokens: 384_000,
    route(request, ctx) {
      // Продолжения/повторы (retry) остаются на предыдущей модели, чтобы кэш не сбрасывался.
      if (request.reason !== "user") {
        const sticky = request.failed ?? request.previous;
        if (sticky)
          return {
            model: sticky.model,
            thinkingLevel: sticky.thinkingLevel ?? "low",
          };
      }
      // Эскалация только по явному high/max.
      if (request.thinkingLevel === "high" || request.thinkingLevel === "max") {
        return routeTo(request, ctx, PRO, request.thinkingLevel);
      }
      return routeTo(request, ctx, FLASH, "low");
    },
  });
}
```

### 12.7 Эталонный код 2: delegate (`.pi/extensions/delegate.ts`)

```ts
import { Type, type TextContent } from "@earendil-works/pi-ai";
import { defineTool, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

const delegateTool = defineTool({
  name: "delegate",
  label: "Delegate",
  description:
    "Run an isolated DeepSeek sub-agent with its own system prompt and a focused task. " +
    "Use for independent work (planning, reviewing, researching) without polluting the main context.",
  parameters: Type.Object({
    role: Type.String({
      description: "System prompt / persona for the sub-agent.",
    }),
    task: Type.String({ description: "The focused task or question." }),
    model: Type.Optional(
      Type.String({
        description: "deepseek-flash (default) or deepseek-v4-pro.",
      }),
    ),
  }),

  async execute(_toolCallId, params, signal, _onUpdate, ctx) {
    const modelId =
      params.model === "deepseek-v4-pro" ? "deepseek-v4-pro" : "deepseek-flash";
    const model = ctx.modelRegistry.find("deepseek", modelId);
    if (!model) {
      return {
        content: [
          {
            type: "text",
            text: `delegate: model deepseek/${modelId} is not available`,
          },
        ],
        details: { error: "model-not-found", modelId },
        isError: true,
      };
    }
    const reasoning = modelId === "deepseek-v4-pro" ? "high" : "low";
    try {
      const stream = ctx.modelRegistry.streamSimple(
        model,
        {
          systemPrompt: params.role,
          messages: [
            { role: "user", content: params.task, timestamp: Date.now() },
          ],
        },
        { reasoning, maxTokens: 8_000, signal },
      );
      const message = await stream.result();
      const text = message.content
        .filter((block): block is TextContent => block.type === "text")
        .map((block) => block.text)
        .join("\n")
        .trim();
      if (message.stopReason === "error" || message.errorMessage) {
        return {
          content: [
            {
              type: "text",
              text: `delegate error: ${message.errorMessage ?? "unknown"}`,
            },
          ],
          details: { error: message.errorMessage, modelId },
          isError: true,
          usage: message.usage,
        };
      }
      return {
        content: [{ type: "text", text: text || "(empty response)" }],
        details: { modelId, stopReason: message.stopReason },
        usage: message.usage,
      };
    } catch (error) {
      return {
        content: [{ type: "text", text: `delegate failed: ${String(error)}` }],
        details: { error: String(error), modelId },
        isError: true,
      };
    }
  },
});

export default function (pi: ExtensionAPI) {
  pi.registerTool(delegateTool);
}
```

Ключевые идеи: `ctx.modelRegistry.find` → модель; `streamSimple` + `await stream.result()` → финальный
`AssistantMessage`; `usage` пробрасывается в результат, чтобы сессия корректно считала стоимость субагента;
валидация на границе и явная ошибка при обрыве/аборте вместо молчаливого «(empty response)».

## 13. MCP и LSP: как к агенту подключаются инструменты

В разделе 12 мы писали инструменты сами. Но чаще писать не нужно — достаточно подключить готовые. Для
этого в мире кода и ИИ-агентов есть два стандарта: **LSP** (как программа «понимает» код) и **MCP** (как
агент подключает чужие инструменты). Сначала разберём оба на бытовых примерах, затем — на нашем проекте.

### 13.1 LSP простыми словами

Представь библиотеку. Плохой помощник умеет только искать слово «яблоко» во всех книгах: найдёт каждое
упоминание, но не отличит фрукт от названия компании. Хороший помощник понимает смысл: «вот определение,
вот ссылки, вот опечатка».

С кодом так же. `grep` (и агент с ним) видит код **как текст** — строки и слова. Он найдёт все вхождения,
но не отличит функцию от переменной с тем же именем, не покажет типы и не переименует безопасно.

Смысл кода понимает **языковой сервер** (language server) — программа-эксперт по конкретному языку. Она
разбирает код в дерево символов и отвечает на вопросы: где определение, кто ссылается, какие типы, где
ошибки, как безопасно переименовать.

Редактор и языковой сервер общаются по открытому стандарту **LSP (Language Server Protocol)** — это
общее соглашение о том, как редактор (VS Code, Zed, Neovim…) и сервер-эксперт обмениваются данными.
Один язык — один сервер: для TypeScript это `vtsls`, для Rust — `rust-analyzer`, для Python —
`basedpyright`. Благодаря единому протоколу «умную навигацию» получает любой редактор с поддержкой LSP.

Зачем это агенту? Агент читает код как текст — то есть оказывается в той же ситуации, что «плохой
помощник». Дай ему доступ к языковому серверу — и он сможет спрашивать то же, что человек в редакторе.
Именно это делает **Serena** (раздел 13.4).

### 13.2 MCP простыми словами

У ноутбука есть порты: любое устройство с USB-C — мышь, диск, монитор — подключается и работает. До
USB у каждого устройства был свой разъём, и это было неудобно.

**MCP (Model Context Protocol)** — это такой «единый разъём» для ИИ-агентов: открытый стандарт, по которому
программа-сервер отдаёт агенту инструменты (функции) с именами, описаниями и параметрами, а агент
(клиент) их находит и вызывает. Любой MCP-сервер совместим с любым MCP-клиентом — писать код под каждый
агент не нужно.

Три роли:

- **MCP-сервер** — программа с инструментами: Serena («найди символ»), Playwright («открой страницу»),
  Postgres («выполни запрос»). В pi запускается отдельным процессом, обычно по транспорту `stdio`
  (общение через stdin/stdout).
- **MCP-клиент (хост)** — среда, где живёт агент (наш pi). Подключается к серверам, получает список
  инструментов и даёт модели их вызывать.
- **Транспорт** — как они связаны: `stdio` (локальный процесс; основной вариант в pi) или streamable
  HTTP. Устаревший `sse` pi не поддерживает.

Подключение в pi — командой; конфиг — `~/.pi/agent/mcp.json` (глобально) или `.pi/mcp.json` (проект):

```bash
pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
pi mcp add docs --url https://example.com/mcp --bearer-token-env-var DOCS_TOKEN
pi mcp list          # проверка
```

Формат — стандартный `mcpServers`:

```jsonc
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."],
    },
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "exposure": "deferred",
    },
  },
}
```

**Exposure** — как модель добирается до инструментов сервера (десятки чужих инструментов не должны
раздувать промпт):

| Режим                | Поведение                                                 | Когда                                        |
| -------------------- | --------------------------------------------------------- | -------------------------------------------- |
| `codemode` (default) | вызывается из codemode-скриптов, модели не декларируется  | общие серверы, объединять/фильтровать вызовы |
| `deferred`           | не декларируется, пока `tool_search` не найдёт совпадение | большие серверы                              |
| `direct`             | декларируется модели как обычный инструмент               | маленькие частые наборы                      |
| `hidden`             | зарегистрирован, но недоступен                            | выключить/секретные                          |

`toolExposure` переопределяет exposure для отдельных инструментов (ключи = имена, `*` — wildcard).
Инструменты именуются `mcp__<server>__<tool>`. Внутри сессии — `/mcp` (статус, sign-in, exposure).

Бытовое сравнение: `direct` — инструменты на столе (модель видит сразу); `deferred` — в ящике (достаются
через `tool_search`, когда понадобились); `codemode` — в подсобке (доступны из скриптов); `hidden` — заперты.

### 13.3 Как это используют агент, субагенты и харнесс

- **Харнесс** (`.pi/`) — «пульт»: какие MCP-серверы подключены, что им разрешено (`exposure`), какие
  настройки. Это `.pi/mcp.json`, `.pi/settings.json`, `.pi/extensions/`.
- **Агент** (pi) при старте подключает серверы, узнаёт их инструменты и во время работы вызывает их
  наравне со встроенными (`read`, `edit`) и нашими (`delegate`). Модель не знает происхождения
  инструмента: для неё это просто `tool_call`.
- **Субагенты** (`subagent`/`delegate`) — отдельные процессы pi со своим контекстом. Они подключаются
  к тем же MCP-серверам, поэтому «помощник» для ревью может сам вызвать Serena (если доступ к этому
  инструменту ему разрешён).
- **Инструменты** бывают трёх происхождений: встроенные в pi, из расширений (раздел 12) и из MCP-серверов
  (этот раздел). Для модели разницы нет.

Один вызов целиком (пример — переименовать функцию):

```
пользователь: «переименуй loadCfg в loadConfig»
  → агент: tool_call mcp__serena__find_referencing_symbols(loadCfg)
     → Serena (MCP-сервер) спрашивает по LSP языковой сервер:
        «кто ссылается на символ loadCfg?» → vtsls возвращает точные места
     ← Serena отдаёт агенту несколько компактных результатов вместо десятков файлов
  → агент: rename_symbol(...) → Serena делает безопасный rename через LSP
```

`grep` нашёл бы все вхождения слова, включая строки и комментарии; связка **MCP (Serena) + LSP (vtsls)**
даёт семантику — точные символы и безопасные правки.

### 13.4 Serena: семантические инструменты кода (MCP + LSP)

**Что это.** Serena — открытый набор инструментов, который даёт ИИ-агенту «понимание» кода: она
поднимает языковые серверы (LSP) и отдаёт их возможности агенту как MCP-инструменты — семантический
поиск и безопасное редактирование. Написана на Python, ставится через `uvx` (пакет `serena-agent`) и в
нашем проекте работает как MCP-сервер.

**Как это работает по шагам.** pi запускает Serena как MCP-сервер → Serena поднимает языковые серверы из
`.serena/project.yml` (у нас TypeScript/markdown/yaml/json) → когда агент вызывает, например,
`find_symbol`, Serena переводит запрос в LSP-вопрос языковому серверу → ответ возвращается агенту. Живая
копия — `.pi/mcp.json` + `.serena/project.yml`, заготовка — `templates/mcp/`.

```jsonc
// .pi/mcp.json
{
  "mcpServers": {
    "serena": {
      "command": "uvx",
      "args": [
        "--from",
        "serena-agent",
        "serena",
        "start-mcp-server",
        "--context",
        "ide",
        "--project-from-cwd",
      ],
      "description": "LSP-based semantic code tools: symbols, references, definitions, and code search (Serena).",
      "exposure": "deferred",
      "env": { "PYTHONUTF8": "1" }, // cp1251-Windows: форсируем UTF-8 в stdio
    },
  },
}
```

- PyPI-пакет `serena-agent`, entrypoint — `serena`; без `--from` uvx не найдёт бинарь.
- **`--context ide`** — pi уже имеет read/edit/grep/find, поэтому Serena режется до 22 семантических +
  memory-инструментов (без дублей). Для клиента без собственных инструментов — `claude-code`/`agent`.
- **`--project-from-cwd`** — pi запускает stdio-сервер из корня проекта, Serena сама находит ближайший
  `.serena/project.yml` (без хардкода путей).
- **`.serena/project.yml`** — список `language_servers` (typescript/markdown/yaml/json для этого репо;
  полный список языков — в docs Serena). `project.local.yml` и `logs/`/`memories/` — машинно-локальные, не коммитятся.
- **Проверка:** `pi mcp list` (→ `serena: connected, 22 tools`) и
  `uvx --from serena-agent serena project health-check .` (действительно запускает LS и вызывает symbol-инструменты).

**Что умеют её инструменты (после `--context ide` — 22 штуки):**

- **Навигация и анализ:** `get_symbols_overview`, `find_symbol`, `find_referencing_symbols`,
  `find_implementations`, `find_declaration`, `search_for_pattern`, `get_diagnostics_for_file`.
- **Правки:** `replace_symbol_body`, `insert_before_symbol`, `insert_after_symbol`, `replace_content`,
  `replace_in_files`, `rename_symbol`, `safe_delete_symbol`.
- **Память проекта (memories):** `write_memory`, `read_memory`, `list_memories`, `edit_memory`,
  `rename_memory`, `delete_memory`, `onboarding`, `initial_instructions`.

**Как этим пользоваться:**

- Агенту — словами: «найди определение функции `split_window`», «кто вызывает `load_config`», «переименуй
  `loadCfg` в `loadConfig`». Он сам найдёт нужный инструмент через `tool_search` и вызовет `mcp__serena__*`.
- Посмотреть список подключённых инструментов: `/mcp` в pi (или `pi mcp list`).
- **Memories** — заметки Serena о проекте; лежат в `.serena/memories/` и помогают «ввести агента в курс»
  (`onboarding`/`initial_instructions`). Машинно-локальные, в репозиторий не коммитятся.
- Увидеть, что именно Serena делает «под капотом», и потрогать её настройки можно через её веб-дашборд
  (раздел 13.5).

### 13.5 Дашборд Serena: что, зачем и как читать

У Serena есть встроенный **веб-дашборд** (включён по умолчанию) — локальная страница, через которую
видно, что Serena делает, и можно менять её настройки. В нашем проекте он уже работает:
`http://127.0.0.1:24282/dashboard/index.html` (порт 24282; если занят, Serena возьмёт следующий).

**Как открыть:**

- автоматически при старте (в `~/.serena/serena_config.yml`: `web_dashboard_open_on_launch: true`);
- вручную в браузере: `http://localhost:24282/dashboard/index.html`;
- отдельным окном: `uvx --from serena-agent serena dashboard-viewer http://localhost:24282/dashboard/index.html`.

> Открытие «словами» (инструмент `open_dashboard`) Serena включает, только когда автооткрытие выключено; у
> нас автооткрытие включено, и в наборе `--context ide` такого инструмента нет — открываем по ссылке.

**Что на нём есть и зачем:**

| Раздел | Что показывает | Зачем |
|---|---|---|
| Обзор (status/config) | активные инструменты, языки, режимы и контексты | понять, с чем Serena реально работает сейчас |
| Вызовы инструментов | текущие и прошлые вызовы + статистика | видеть, что агент спросил у Serena и что она ответила; ловить лишние вызовы |
| Логи | живой лог | разбирать ошибки, почему инструмент «молчит» |
| Настройки | смена активных языков «на лету» | быстро подстроить Serena под проект |
| Редакторы | `serena_config.yml`, `.serena/project.yml`, memories проекта | править конфиг и заметки без ручного поиска файлов |
| Завершение | остановка MCP-сервера Serena | аккуратно закрыть сервер |

**Настройки дашборда** (`~/.serena/serena_config.yml`; у нас такие):

| Ключ | У нас | Смысл |
|---|---|---|
| `web_dashboard` | `true` | дашборд включён |
| `web_dashboard_open_on_launch` | `true` | открывать окно при старте Serena |
| `web_dashboard_interface` | (пусто) | способ показа: нативная обёртка / трей / браузер |
| `web_dashboard_listen_address` | `127.0.0.1` | слушать только локально |
| `web_dashboard_trusted_hosts` | `[127.0.0.1, localhost]` | доверять только локальным хостам |

Отключить автооткрытие: флаг `--open-web-dashboard False` у `start-mcp-server` или
`web_dashboard_open_on_launch: false`. Безопасность: дашборд слушает только `127.0.0.1` и доверяет только
`localhost` — снаружи недоступен.

Отдельно есть **GUI Log Viewer** — устаревшее приложение (в основном для Windows), показывает живой лог
в отдельном окне; у нас выключено (`gui_log_window: false`). Включается `gui_log_window: true`.

### 13.6 Playwright MCP — реальный браузер

`@playwright/mcp` даёт агенту настоящий браузер (navigate/click/fill/snapshot/screenshot) вместо
«представь, что страница выглядит так» — фактические DOM-снапшоты и скриншоты.

```jsonc
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": [
        "-y",
        "@playwright/mcp@latest",
        "--headless",
        "--caps",
        "vision",
        "--file-paths",
        "relative",
        "--output-dir",
        ".playwright-mcp",
      ],
      "exposure": "deferred",
    },
  },
}
```

- **`--headless` обязателен** — у сервера по умолчанию режим headed (окно на каждый запуск). `--caps vision` — модель
  получает скриншоты. Профиль персистентный (логины переживают сессии); `--isolated` — для одноразовых.
- Браузеры: `npx playwright install chromium`. Скриншоты пишутся в `.playwright-mcp/`.
- **LSP не нужен:** тесты — обычный TypeScript, покрывается `vtsls` (Zed) / `typescript` (Serena).

### 13.7 PostgreSQL MCP — схема и запросы

`@henkey/postgres-mcp-server`: исследование схемы, SQL-запросы (в том числе с параметрами), экспорт/импорт
данных. Подключён с
`"enabled": false` — локально нет ни psql, ни docker, ни `DATABASE_URL` (сервер, падающий при каждом
старте, — шум, а не безопасность).

```jsonc
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@henkey/postgres-mcp-server@latest"],
      "env": { "POSTGRES_CONNECTION_STRING": "${DATABASE_URL}" }, // pi раскрывает ${VAR} в env
      "exposure": "deferred",
      "enabled": false, // включить: export DATABASE_URL=... → /mcp → Enable
    },
  },
}
```

- **Секреты не коммитятся:** строка подключения живёт в `DATABASE_URL` (shell profile), в репо — только `${DATABASE_URL}`.
- **Встроенного SQL-сервера нет** — у Zed только подсветка и форматирование (`sql-formatter`), у Serena
  SQL нет в списке языков. Семантику даёт Postgres MCP.

### 16.3 Типичные ошибки (каждая — из реального опыта)

- **`pi --print` наследует env родителя:** запущенный из сессии pi, он получит `PI_MODEL` / `PI_PROVIDER`
  / `PI_REASONING_LEVEL` и проигнорирует `defaultModel` из settings.json. Для проверок задавай модель
  явно: `--model deepseek/deepseek-flash --thinking low`. `--model` принимает `provider/id` и суффикс
  `:<thinking>`.
- **cp1251-Windows и эмодзи.** Python на русской локали пишет в консоль в cp1251; `serena project
health-check` печатал «✅ Health check passed» и падал `UnicodeEncodeError` — **exit 1 при реальном
  успехе**. Вывод: не полагаться только на код возврата — читать текст вывода. Лечится `env: { "PYTHONUTF8": "1" }`
  для MCP-сервера.
- **Playwright MCP по умолчанию headed** — на каждый запуск открылось бы окно браузера. Нужен явный
  `--headless` (+ `--caps vision`, `--output-dir .playwright-mcp`, `--file-paths relative`).
- **Встроенного SQL-сервера нет** — у Zed только подсветка и форматирование, у Serena SQL не в списке
  языков. «LSP для PostgreSQL» — это в строгом смысле не LSP, а семантический слой Postgres MCP +
  `sql-formatter`.
- **Не подключай сервер, который заведомо не подключится.** Без psql/docker/`DATABASE_URL` Postgres MCP
  стоит с `"enabled": false`. Включается одной командой в `/mcp`, когда база появится.
- **Секреты — только через env.** `${DATABASE_URL}` в `env` раскрывается pi; в репозитории — только имя
  переменной.
- **Zed project settings — не всё проектно.** `.zed/settings.json` перекрывает global, но `theme`,
  `vim_mode`, `base_keymap` работают только в user settings; `keymap.json` — вообще только global.
- **Git: `git mv` + `git commit` без путей коммитит весь индекс.** Staged-rename попал в «чужой» коммит.
  Лечится `git reset --soft <base>` + путь-скоупные коммиты (безопасно, пока не запушено). Перед коммитом —
  `git status`, коммить явными путями.
- **Не плоди md-файлы, рассинхроненные с кодом.** Код — источник истины; устаревшие md заставляют агента
  вести себя непредсказуемо и расходовать токены впустую.

### 16.4 Методология настройки (что сработало)

1. **Разведай** текущее состояние (`ls ~/.pi/agent`, `.pi/mcp.json`, Zed settings).
2. **Не изобретай ключи.** Схему — из первоисточника: pi MCP → `docs/mcp.md` в установке; Zed →
   `assets/settings/default.json` в репо `zed-industries/zed`; Serena → `serena <cmd> --help` и её docs.
3. **Сконфигурируй → проверь реальным подключением** (`pi mcp list` показывает tool count и ошибки), а не
   парсингом JSON.
4. **Оформи шаблон** в `templates/`, обнови этот документ, закоммить.

Правило: «ключ, которого я не видел в схеме/help — не пишу». Это дешевле, чем отладка сломанной конфигурации.

5. **Заведи поведенческий gate, а не только конфиг-чек.** Конфиг-тест (правила на месте, ссылки резолвятся)
   зелёный — но деньги всё равно текли, потому что правило «flash-default» нарушалось на практике. Спас
   `pi-cost --health` (§ 16.1, «комплексный аудит»): он сравнивает фактическую долю стоимости v4-pro с порогом
   и падает с exit 1 при нарушении. Правило: проверять трату **поведением** (реальными usage-числами), а не
   только наличием правил в файле.

### 16.5 Конфликт расширений: глобальная и проектная копии (fix 2026-10-23)

**Симптом.** `pi` в проекте не стартует:

```
Error: Failed to load extension "~/.pi/agent/extensions/delegate.ts": Tool "delegate" conflicts with ./.pi/extensions/delegate.ts
Hint: Start without extensions using "pi -ne".
```

**Причина.** Один и тот же инструмент `delegate` зарегистрирован из двух файлов сразу: проектного
`.pi/extensions/delegate.ts` и глобального `~/.pi/agent/extensions/delegate.ts`. Одно имя tool из двух
разных файлов pi считает фатальным конфликтом (проверка `detectExtensionConflicts` в бандле pi 1.3.0).
Конфликтуют только **tools и флаги** — команды и виртуальные модели перерегистрируются без ошибки,
поэтому `deepseek-balance.ts` (команда `balance`) и `deepseek-router.ts` (виртуальная модель `auto`)
конфликта не дали. Копии были идентичны по содержимому: `diff --strip-trailing-cr` → exit 0
(различались только CRLF/LF).

**Как получилось.** В проекте живут два контура — встроенный агент Zed (читает AGENTS.md и проектные
файлы) и харнесс pi.dev (`~/.pi/agent/`). При переносе расширений в global по «Варианту A» (§ 17.2)
проектные копии не удалили — переключение между контурами это не чинит: при каждом старте `pi`
загружает оба скоупа и падает на дубле.

**Фикс.** Удалять копии не обязательно. Проектные расширения грузятся первыми, поэтому глобальной
копии `delegate.ts` добавлен guard: если в проекте есть своя копия — глобальная уступает:

```ts
import { existsSync } from "node:fs";
import { join } from "node:path";
import { CONFIG_DIR_NAME, defineTool, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  // Project-local extensions load first; if this project ships its own copy,
  // registering the same tool again would be a hard load conflict.
  if (existsSync(join(process.cwd(), CONFIG_DIR_NAME, "extensions", "delegate.ts"))) return;
  pi.registerTool(delegateTool);
}
```

⚠️ Проверить «уже зарегистрирован ли tool» через `pi.getAllTools()` в фабрике расширения нельзя:
на фазе загрузки action-методы заблокированы и бросают «Extension runtime not initialized». Поэтому
детект — файловой системой, а не через API.

**Проверка (без расхода токенов).**

```bash
pi -p "say ok" --model deepseek/flash --api-key invalid-key-for-test
# ожидаемо: только 401 от DeepSeek (ключ намеренно невалидный), «Failed to load extension» — нет
```

Глубже — временная диагностическая расшира, печатающая `pi.getAllTools()` в `session_start`:
`delegate` в списке ровно один раз, ошибок загрузки нет. (`--tools delegate` для проверки НЕ годится:
неизвестные имена в allowlist молча игнорируются — проверено на `no_such_tool_xyz`.)

**Профилактика.** Держи каждое расширение в одном скоупе: либо только проект (`.pi/extensions/`),
либо только global (`~/.pi/agent/extensions/`), как в таблице § 17.1. Если копии в обоих — обязателен
такой guard, иначе конфликт вернётся при следующем `cp` без удаления исходников.

## 17. Перенос опыта в другие проекты

Опыт переносится в новые проекты — но **не копированием папки целиком**: у pi есть глобальный
(user) и проектный уровни ресурсов, раскладывай их по двум критериям — цена контекста и дрейф копий.

### 17.1 Инвентарь: что куда

| Ресурс                                                      | Куда оптимально                                 | Почему                                                                                                                                 |
| ----------------------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Общие правила: token-economy, Гамильтон/Акин, DeepSeek      | **global**: `~/.pi/agent/AGENTS.md`             | всегда в контексте → одна копия вместо N, контекст короче                                                                              |
| Специфика репо: структура, команды, пути                    | **проект** (короткий шаблон)                    | уникально для каждого репозитория                                                                                                      |
| `deepseek-router.ts`, `delegate.ts`, `deepseek-balance.ts`  | **global**: `~/.pi/agent/extensions/`           | чистые инструменты, не зависят от проекта                                                                                              |
| `/plan`, `/review`, `/ship`                                 | **global**: `~/.pi/agent/prompts/`              | workflow один на все проекты                                                                                                           |
| `code-review`, `engineering-principles`                     | **global**: `~/.pi/agent/skills/`               | типовая экспертиза; reference-пути относительны skill-директории                                                                       |
| `defaultTools`, `hideThinkingBlock`, `showCacheMissNotices` | **global**: `~/.pi/agent/settings.json`         | тогда новый проект = ноль конфига                                                                                                      |
| `tools/pi-cost/`                                            | проект: **junction** (ссылка каталога) на канон | один файл-источник, без копий                                                                                                          |
| MCP+LSP: `templates/mcp/`                                   | **шаблон**: копировать в каждый проект          | `language_servers`/`project_name` уникальны для репо; `--project-from-cwd` и `${DATABASE_URL}` делают записи переносимыми без секретов |
| Zed LSP: `templates/zed-lsp/`                               | **шаблон**: копировать `.zed/settings.json`     | `languages`/`tab_size` уникальны для репо; keymap.json — только global                                                                 |
| `PI_ZED_DEEPSEEK_MASTERY.md`                                | **остаётся здесь**                              | знание-база; в новые проекты не копируется                                                                                             |

Почему так: (1) **токены** — AGENTS.md и описания инструментов грузятся в каждый сеанс, дублировать их
по проектам = платить за тот же текст N раз; (2) **дрейф копий** — расходящиеся копии (мы сами допустили:
29- и 45-законные версии Акина); (3) **trust** — проектные ресурсы требуют подтверждения в каждом новом
проекте, глобальные доверены один раз.

### 17.2 Вариант A — быстрый: копирование в global (один раз)

```bash
SRC=/путь/к/этому/репозиторию
mkdir -p ~/.pi/agent/skills
cp -r $SRC/.pi/skills/code-review $SRC/.pi/skills/engineering-principles ~/.pi/agent/skills/
cp $SRC/.pi/extensions/deepseek-router.ts $SRC/.pi/extensions/delegate.ts ~/.pi/agent/extensions/
cp $SRC/.pi/prompts/plan.md $SRC/.pi/prompts/review.md $SRC/.pi/prompts/ship.md ~/.pi/agent/prompts/
```

⚠️ Если проектные копии расширений остаются на месте — в глобальном `delegate.ts` должен стоять
guard (см. § 16.5), иначе `pi` в этом проекте не стартует: `Tool "delegate" conflicts with ...`.
Либо удали проектные копии после `cp` — тогда guard не нужен, но репозиторий теряет самодостаточность
(свежий клон без global-настройки не получит `delegate`).

- Общие правила из `AGENTS.md` — в `~/.pi/agent/AGENTS.md`; в проектном файле остаётся только специфика репо.
- В `~/.pi/agent/settings.json` добавить `defaultTools`, `hideThinkingBlock`, `showCacheMissNotices`.
- Плюс: быстро, без инфраструктуры. Минус: обновление = снова копировать (дрейф возможен).

### 17.3 Вариант B — канон без дрейфа: pi-пакет

`pi install` ставит пакет с extensions+skills+prompts одним пакетом (npm/git/local path; см.
`docs/packages.md`). Структура пакета-канона:

```text
pi-harness/
├── package.json      # {"name":"zed-pi-harness","keywords":["pi-package"]}
├── extensions/       # deepseek-router.ts, delegate.ts
├── skills/           # code-review/, engineering-principles/
└── prompts/          # plan.md, review.md, ship.md
```

```bash
pi install ./pi-harness        # personal (global, все проекты)
pi install -l ./pi-harness     # только в текущий проект (.pi/settings.json)
pi install git:github.com/<you>/zed-pi-harness@v1   # версионированно, обновление: pi update --extensions
```

- **Local path грузится из пути без копирования** → правишь канон в одном месте, все проекты видят
  изменения сразу. Копии не расходятся.
- Хост-пакеты (`@earendil-works/pi-ai`, `pi-coding-agent`) — в `peerDependencies: {"*"}`, не в
  `dependencies` (иначе дубликат классов и warning).
- Проектные пакеты грузятся только после подтверждения trust.
- Если пойдёшь по B — этот репозиторий тоже переведи на пакет (иначе здесь останется старая копия).

**Рекомендация:** A сейчас, B — когда появится третий проект (не строить пакет раньше, чем появились
потребители; global-уровень ничего не блокирует).

### 17.4 Чек-лист нового проекта

```bash
mkdir myproject && cd myproject && git init
# 1. .gitignore: node_modules/, auth.json, *.log
# 2. проектный AGENTS.md — только специфика репо (общие правила уже в global)
# 3. pi-cost — junction на канон вместо копии (Windows, cmd; junction требует абсолютные пути):
cmd //c "mklink /J <новый-проект>\tools\pi-cost <путь-к-этому-репозиторию>\tools\pi-cost"
#    (предварительно mkdir tools в новом проекте; альтернатива — git subtree)
# 4. MCP+LSP: скопировать templates/mcp/mcp.json → .pi/mcp.json (убрать лишние серверы;
#    для serena также serena.project.yml → .serena/project.yml; поправить project_name + language_servers)
# 5. Zed LSP: скопировать templates/zed-lsp/settings.json → .zed/settings.json;
#    поправить languages + tab_size под репо
# 6. запустить pi в папке → подтвердить trust → /reload
```

Проверка переноса — числами, не мнениями:

```bash
pi --print "Reply with exactly: OK"                       # расширения скомпилировались
pi --print "Is skill engineering-principles in your skills list? yes/no"   # skill виден модели
node tools/pi-cost/pi-cost.mjs --last 1                   # стоимость первой сессии в новом проекте
```

Дополнительно для проектов на **Zed-харнессе** (правила в `.agents/`, а не `.pi/`):

```bash
node tools/token-thrift-check.mjs      # правила экономии в AGENTS.md + ссылки резолвятся
node tools/harness_check.mjs           # навыки/роли/MCP/LSP/memory целиком
# и главный поведенческий gate — в этом репозитории (канон pi-cost):
node tools/pi-cost/pi-cost.mjs --health --last 7
```

`--health` смотрит фактические usage-числа по всем pi-сессиям машины (не один проект), поэтому его
держат в этом репозитории, а не копируют в каждый проект — он диагностирует **поведение** (долю v4-pro,
cache-hit), а не конфиг конкретного репозитория.

### 17.5 Что НЕ переносить

`sessions/`, `auth.json`, `trust.json`, `models-store.json` — машинно-специфичны (токены, доверие,
история). Никогда не копируй `~/.pi/agent` целиком и не коммить `auth.json`.

## 18. MCP без переплаты токенов

Правила для агента — в скилле `mcp-usage` (`.pi/skills/mcp-usage/`). Здесь — суть.

### 18.1 В чём проблема

MCP — удобный способ подключать к агенту чужие инструменты. Но обычный способ его использования
дорог по двум причинам:

1. **Платишь за инструменты, которыми не пользуешься.** При подключении сервера в контекст модели
   попадают описания всех его инструментов — и повторяются в каждом запросе, даже если ни один не
   вызывался. Один большой сервер может стоить порядка 10 тысяч токенов за ход (оценка, не измерено),
   несколько серверов — и значительная часть окна потрачена впустую.
2. **В контексте оседают промежуточные результаты.** Каждый ответ инструмента возвращается модели:
   десять вызовов — десять блоков в истории, хотя нужен только итог.

Поэтому отказ от «всегда включённых» MCP-инструментов — решение про **бюджет контекста**, то есть про
деньги, а не про «не нравится протокол». Альтернатива — **скиллы**: это просто файл с инструкцией,
который агент читает только когда задача совпала с его описанием. Пока не понадобился — стоит ноль.

### 18.2 Как pi экономит на этом

У каждого инструмента есть режим видимости:

- **deferred** — инструмент не показывается модели, пока она не поищет нужную возможность
  (`tool_search`); после находки остаётся доступным до конца ветки.
- **codemode** (по умолчанию) — инструмент виден только скриптам: модель вызывает их пачкой,
  а в контекст попадает только итог.
- **direct** — инструмент объявлен модели как обычный встроенный. Только для маленьких наборов,
  которые нужны каждый ход.

Плюс экономия из коробки: серверы подключаются в фоне и по потребности; в системном промпте от
сервера остаётся одна строка описания, а не все схемы; большие ответы (больше 20 КБ) доходят до
модели обрезанными, полный текст сохраняется во временный файл.

### 18.3 Почему кажется, что pi «не использует MCP»

1. Инструменты невидимы, пока их не поискали, — а это лишний шаг.
2. Серверы поднимаются лениво, а не висят готовыми с самого старта.
3. По умолчанию модель пишет скрипт и видит только его итог — экономно, но для одного простого
   вызова выглядит «непрямо».
4. Часть возможностей протокола (подсказки, интерфейсы, фоновые задачи) в базовой реализации
   слабее; полнее — через пакет `pi-mcp-adapter`.

### 18.4 Правило выбора

| Задача | Что выбрать | Цена, пока не нужно |
| --- | --- | --- |
| Частая узкая операция | скилл или консольная команда | ноль |
| Большая внешняя система (браузер, база данных, GitHub/Jira) | MCP-сервер в режиме deferred | одна строка описания |
| Небольшой набор инструментов на каждый день | режим direct | описания всего набора |
| Много однотипных вызовов | один скрипт, который делает их пачкой | только итог |

- Новую возможность сначала закрывай скиллом или скриптом; MCP — только для того, что скриптами не
  закрыть.
- Инструменты режима deferred ищи через `tool_search`, имена не выдумывай.
- Каждый вызов проверяй на ошибку и таймаут; упавший вызов не выдавать за успех.
- «Дорого/дёшево» — только с цифрой из `pi-cost`, не на ощущениях.
- Не меняй набор инструментов посреди сессии: стабильный контекст держит кэш тёплым.

### 18.5 В других агентных средах

В некоторых средах (например, редакторах с собственной MCP-поддержкой) отложенной загрузки нет:
всё, что подключено, показывается модели каждый ход. Там правило ещё строже: подключай только то,
чем действительно пользуешься, и убирай, когда перестало быть нужно. Скилл переносится с этой
поправкой.

### 18.6 Источники

- Официальная документация pi (раздел про MCP-серверы): режимы видимости, поиск инструментов,
  ленивый запуск, обрезка результатов.
- Статьи и пакеты: гайд по расширениям pi, заметка «MCP в pi», пакеты `pi-mcp-adapter` и `pi-mcp`
  (ссылки — в скилле `mcp-usage`).
- Несколько видеообзоров на тему «скиллы вместо MCP». Не просматривались — пересказ по описаниям
  владельца; точные ссылки — в скилле `mcp-usage`.

## 19. Защита секретов

Правила — в скилле `secret-leak-guard` (`.pi/skills/secret-leak-guard/`), там же подробное
исследование. Проверки выполнены 2026-10-24 на pi 1.3.0.

### 19.1 Главный принцип: что прочитано — то ушло

Всё, что агент прочитал или что вернулось из команды, уходит к провайдеру модели в следующем же
запросе и остаётся в истории сессии.

| Что произошло | Ушло ли наружу | Чем закрыто |
| --- | --- | --- |
| Агент прочитал файл с ключами | да, сразу | правило «не читать», блокировка чтения |
| Команда напечатала пароль | да, и осталось в истории | блокировка команд, вырезание секретов из вывода |
| Секрет попал в git-коммит | да, навсегда | проверка коммитов сканером |
| Модель сама догадалась о секрете | да, отозвать нельзя | только правило поведения |

Отсюда: вырезание секретов из вывода — страховка от случайности, а не гарантия. Если секрет уже
попал в контекст — сначала сменить ключ (ротация), потом разбираться с историей.

### 19.2 Встроенной защиты в pi нет

В официальной документации pi ни одного механизма скрытия секретов нет: есть файл для хранения
ключей доступа и команды управления ими — и всё. Документация прямо предупреждает: наблюдение за
транскриптом и доверие проекту — не граница безопасности. Телеметрия установки включена по
умолчанию, но содержимое файлов не отправляет; отключается в настройках при желании.

### 19.3 Расширение pi-heimdall: помогает, но не граница

Готовое открытое расширение `pi-heimdall` закрывает очевидные дыры:

- запрещает читать файлы с ключами (`.env` и подобные); образцы настроек `.env.example` остаются
  доступны — это задумано;
- запрещает команды, где упоминаются имена секретов из файла-списка;
- вырезает значения секретов из вывода команд, в том числе в кодировке base64.

Проверено вживую: чтение файла ключей блокируется, команда с именем секрета блокируется, секрет из
однострочного вывода вырезается.

Найден и **предел**: если команда кодирует в base64 сразу несколько строк (типичный файл с ключами),
вырезание не срабатывает, и секрет доходит до модели. Причина зафиксирована в скилле: расширение
ищет закодированную строку ровно с хвостом из символов `==`, а в кодировке нескольких строк такого
куска нет.

Вывод: расширение ставить стоит — оно ловит случайные утечки. Полагаться только на него нельзя.

### 19.4 Проверка коммитов: gitleaks

Открытый сканер `gitleaks` находит ключи и токены известных форматов (AWS, GitHub, Slack, OpenAI и
сотни других) прямо в коммитах. Проверено: подложенные ключи находит, чистый коммит пропускает, при
находке коммит блокируется.

Пределы, тоже проверенные: нестандартные короткие ключи собственного формата он не видит (ловит
только известные шаблоны), а режим чтения с клавиатуры не работает — нужно сканировать файлы.
Поэтому он — последний рубеж, а не единственная защита.

### 19.5 Пять слоёв защиты (внедрены в этот репозиторий)

1. **Не хранить то, что нельзя коммитить.** Файлы с ключами внесены в `.gitignore` (кроме образца
   `.env.example`).
2. **Список имён секретов** в отдельном файле — по нему расширение понимает, что вырезать. Значения
   в файле не хранятся.
3. **Расширение pi-heimdall** — блокировки и вырезание (см. выше).
4. **Проверка при коммите.** Перед каждым коммитом сканер проверяет изменения; нашёл ключ — коммит
   не проходит. Сканер можно пропустить одной командой, но это осознанное действие, а его отсутствие
   — ошибка, а не «проверено».
5. **Правила поведения.** Не читать и не печатать секреты намеренно; увидел секрет — сказать об этом
   и предложить сменить ключ.

Гейт уже доказал пользу на практике: при подготовке этого раздела он заблокировал коммит, потому что
в примере оказался ключ настоящего формата AWS — заменён на официальный образец. Правило: гейт,
который ни разу не поймал подложенный секрет, не проверен.

### 19.6 Перенос в другие проекты

Переносятся как есть: `.gitignore`, список имён секретов, скрипт проверки коммитов и сам сканер.
Расширение pi-heimdall работает только с pi — в средах без pi остаются слои 1, 2, 4 и 5. Порядок
важен: сначала `.gitignore`, потом всё остальное.

### 19.7 Источники

- Официальная документация pi: безопасность, телеметрия, события расширений.
- Расширение `pi-heimdall`: описание и исходники (npm).
- Сканер `gitleaks` (github.com/gitleaks/gitleaks).

## 20. CI/CD с GitHub Actions

Автоматическая проверка и выкатка кода на GitHub. Правила и подробности — в скилле
`ci-cd` (`.pi/skills/ci-cd/`), всё готовое лежит в `templates/github-actions/`.
Собрано и проверено 2026-10-24.

### 20.1 Что это и зачем

GitHub умеет сам, роботом, проверять каждый пуш в репозиторий: собирается ли код,
проходят ли тесты, не попал ли в коммит ключ или пароль. Ошибка ловится в момент пуша,
а не когда её заметит человек на ревью, — быстрее и дешевле.

Что это даёт:

- сломанный код не доезжает до ревью — он падает на проверках сразу;
- робот не устаёт и не пропускает проверку «по дружбе»;
- ключи и пароли не попадают в репозиторий — их ловит сканер gitleaks.

### 20.2 Как это устроено

Проверки написаны один раз и лежат в общем наборе шаблонов. В каждом проекте — копия
этих проверок плюс маленький файл со своими настройками. Менять в проекте нужно только
этот маленький файл; если поправили сами проверки в шаблоне — обновить их копию в проекте.

| Файл | Что это | Кто его правит |
| --- | --- | --- |
| `workflows/reusable-ci.yml` | сами проверки и их порядок | никто в проектах — общий шаблон |
| `workflows/ci.yml` | настройки конкретного проекта: язык, команды | автор проекта |
| `actions/setup/action.yml` | «как установить язык и зависимости»: node, python, rust, go | никто в проектах |
| `scaffold-ci.mjs` | скрипт, который раскладывает всё это по проекту | — |

Проверки идут от быстрых к медленным, чтобы не тратить время робота зря:

1. проверка на секреты — быстро, самое важное;
2. стиль кода и типы — параллельно;
3. тесты — запускаются, только если первые две ступени зелёные;
4. сборка — только если тесты прошли.

Чего у проекта нет, то и не проверяется: нет тестов — ступень просто пропускается.
Робот проверяет то, что есть, а не то, что хотелось бы.

### 20.3 Правила

1. Проверки должны быть зелёными на своём компьютере до пуша. GitHub — не место
   первого запуска.
2. В проверках кода нет ни одного пароля или ключа — они там просто не нужны. Ключи
   появляются только на выкатке, и GitHub выдаёт их сам на короткое время: ничего не
   надо хранить, и украденный старый ключ становится бесполезен сам.
3. Упавшая проверка — стоп: её чинят, а не выключают. «Проигнорировать ошибку» запрещено.
4. Готовые действия подключаются по номеру версии (например `actions/checkout@v7`),
   а не по слову «последняя» — чтобы чужое обновление не сломало тихо наше.
5. Права у робота минимальные: только читать репозиторий. Новый пуш отменяет старый
   незавершённый прогон — не копим очередь.
6. Зависимости скачиваются один раз и кэшируются — каждый прогон не тянет мир заново.
   Кэш — это скорость, а не способ «починить» проверку.

### 20.4 Как подключить к новому проекту

```bash
node templates/github-actions/scaffold-ci.mjs <путь-к-проекту>
```

Скрипт сам посмотрит на файлы проекта, определит язык (node, python, rust или go),
подберёт команды проверок и разложит файлы в папку `.github/`. Если в проекте уже есть
свой `ci.yml` — откажется перезаписывать без явного разрешения (`--force`). Если язык
определить не удалось — честно скажет об этом.

Проверено вживую: скрипт прогнан на всех четырёх языках, включая ошибочные случаи, —
генерация и все отказы работают как описано.

### 20.5 Агент devops-expert: следит за релизами

Отдельный агент-помощник, файл `~/.pi/agent/agents/devops-expert.md` — там же, где
planner, reviewer, scout и worker. Работает на модели v4-pro: релиз — дело серьёзное,
на его проверке не экономим.

Что делает:

- перед релизом проверяет готовность: проверки зелёные, версия определена, лишних
  ключей в настройках репозитория нет;
- запускает прогон на GitHub и ждёт его конца (`gh run watch`); если шаг упал —
  разбирает по логам, в чём причина;
- после сборки проверяет факт выкатки: релиз существует, файлы на месте, выкатка
  подтверждена логами — а не «вроде бы всё ок»;
- докладывает честно: «выкатка подтверждена» или «НЕ подтверждена — вот что не проверено».

Сам ничего не публикует: не пушит, не создаёт релизы без явной команды человека.
Его дело — проверить и доложить.

Вызов: в pi — `subagent` → `devops-expert`, в задаче пишем, что проверить (например
«проверь готовность репозитория X к релизу v1.2.0»).

### 20.6 Что проверено, а что нет

Проверено (сделано руками, а не заявлено):

- версии всех готовых действий сверены с их живой документацией через Context7;
- три файла настроек проверены на синтаксис — ошибок нет;
- скрипт-генератор прогнан на четырёх языках и на ошибочном вводе;
- коммит с шаблонами прошёл проверку на секреты (gitleaks: «no leaks found»).

Пока не измерено: сколько минут реально занимает прогон на GitHub. Первая настоящая
