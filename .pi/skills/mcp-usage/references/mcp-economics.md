# MCP и токены: почему pi не ставит MCP в ядро (экономика, механика, источники)

Сжатые правила — в `../SKILL.md` (скилл `mcp-usage`). Здесь — полное обоснование.

Каждое утверждение помечено: **✔ проверено** (по официальной документации pi 1.3.0,
`docs/mcp.md` в установке, или по факту этого харнесса), **[оценка]** (число из обсуждения,
не измерено), **[не проверено]** (пока нет прямого источника).

## 1. Почему классический MCP «съедает» токены

Два механизма, и оба — про то, что попадает в контекст модели.

**Механизм 1: схемы инструментов заранее.** Классический MCP-клиент при подключении сервера
кладёт в системный контекст описания и JSON-схемы всех его tools. Модель платит за них в
каждом запросе, даже если ни разу их не вызовет. Один сложный сервер может стоить порядка
**10k+ токенов** [оценка]; несколько серверов — заметная часть окна потрачена ещё до начала
работы.

**Механизм 2: промежуточные результаты остаются в контексте.** Каждый результат tool call
возвращается модели. Цепочка из 10 вызовов оставляет 10 блоков результатов, хотя модели нужен
только итог. Плюс это ломает префикс-кэш хуже: каждый новый результат меняет суффикс истории.

Вывод: дело не в том, что протокол MCP плох, а в том, что дефолтная модель его использования
плохо масштабируется по токенам.

## 2. Что делает pi вместо этого (✔ проверено по docs/mcp.md 1.3.0)

| Механизм pi | Что видит модель | Факт из документации |
|---|---|---|
| `exposure: deferred` | ничего, пока `tool_search` не найдёт совпадение; загруженные инструменты остаются объявленными на ветке | «Not declared until `tool_search` loads a match for the next model call»; «Tools loaded by `tool_search` are recorded in the transcript and remain declared on that branch» |
| `exposure: codemode` (default) | ничего; вызовы из codemode-скриптов, которые сами сокращают результат | «Callable from codemode scripts, but neither declared to the model nor listed in the codemode description» |
| `exposure: direct` | полные схемы, как у встроенных инструментов | «Declared to the model like a built-in tool» — только для маленьких наборов |
| Список серверов в промпте | одна строка-описание на сервер, без схем | «Servers with `codemode` or `deferred` tools are listed in the `mcp_servers` section of the system prompt, with … one line from the configured `description`» |
| Ленивый старт | серверы подключаются в фоне; первый запрос ждёт до 10 с только серверы с `direct` | «Pi connects every enabled server in the background when a session starts … The first prompt waits up to 10 seconds only for servers with `direct` tools» |
| Обрезка больших результатов | текстовые результаты > 20 КБ доходят с вырезанной серединой; полный текст — во временный файл | «Text results over 20 KB reach the model with their middle removed … Codemode scripts receive the complete result and can reduce it before returning output» |
| `pi-mcp-adapter` | заменяет встроенную MCP-поддержку (в т.ч. `/mcp`), если установлен | «An installed extension that registers `/mcp`, such as `pi-mcp-adapter`, replaces the built-in MCP support» |

Историческая деталь из обсуждения: MCP появился в pi не с самого начала, а был добавлен позже
(назывался релиз 0.99) с механизмом, который держит определения вне контекста **[не проверено]** —
в документации 1.3.0 подтверждения этой версии нет; видео, обещанное к завтрашнему дню, должно
её подтвердить или поправить.

Итог: pi не «не умеет MCP», а сознательно не платит за неиспользуемые tool definitions. Стоимость
до первого использования — одна строка описания сервера вместо всех его схем.

## 3. Почему кажется, что pi «не использует MCP в полную силу»

Это не поломка, а видимые стороны тех же trade-off:

1. **Инструменты невидимы до поиска.** Модель видит не все MCP-инструменты напрямую, а должна
   сначала найти их через `tool_search` (или `searchTools()` в codemode) — лишний шаг рассуждения,
   который выглядит как «не использует».
2. **Ленивый запуск серверов.** Серверы стартуют в фоне при старте сессии и подключаются по
   необходимости, а не «висят» готовыми заранее (✔ проверено: подключение в фоне, ожидание только
   для `direct`).
3. **codemode по умолчанию.** Для серверов с `codemode` модель пишет JS-скрипт, который внутри
   sandbox делает несколько MCP-вызовов, а в контекст попадает только финальный результат. Экономно,
   но для одного простого запроса выглядит менее прямолинейно, чем обычный tool call.
4. **Не все возможности протокола равнозначны.** Prompts, elicitation, UI, tasks в базовой
   реализации pi поддерживаются слабее; полноценнее работает через `pi-mcp-adapter` (✔ проверено:
   адаптер заменяет встроенную поддержку целиком, включая `/mcp`).

## 4. Практические правила (развёрнутая версия — в SKILL.md)

| Ситуация | Выбор |
|---|---|
| Частая узкая операция («прочитать issue», grep по репо, вызов внутреннего API) | skill, CLI-скрипт или маленький tool с README — нулевая цена до использования |
| Большая внешняя экосистема (браузер, БД, Linear/GitHub/Jira, поиск) | MCP-сервер с `exposure: deferred`, через adapter/proxy, ленивая загрузка |
| Много однотипных вызовов (десятки записей) | один codemode-скрипт: промежуточные ответы в контекст не попадают |
| Маленький набор инструментов, нужный в каждом ходе | `direct` — и только если набор действительно маленький |

## 5. Числа этого харнесса

- Cache hit vs miss у DeepSeek: ≈ 30–50× дешевле — зафиксировано в `AGENTS.md` (корень репо) и
  разделе 7.5 `PI_ZED_DEEPSEEK_MASTERY.md`. Любое решение, меняющее промпт или набор инструментов,
  влияет на кэш — поэтому правило «стабильный тулсет в течение сессии».
- Стоимость схем одного сложного сервера ≈ 10k+ токенов — **[оценка]** из обсуждения, не измерено.
  Когда появится видео — перепроверить (A16).
- Обрезка результатов: 20 КБ — ✔ проверено (docs/mcp.md 1.3.0).
- Реальный расход сессий — `node tools/pi-cost/pi-cost.mjs` (A1: числа, не мнения).
