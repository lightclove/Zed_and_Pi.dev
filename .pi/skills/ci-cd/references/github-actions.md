## Структура и поток

```
<проект>/.github/
├── workflows/
│   ├── ci.yml              # триггеры + входы. Единственный файл, который проект правит.
│   └── reusable-ci.yml     # канонический конвейер (workflow_call). Не форкается.
└── actions/setup/action.yml  # composite: тулчейн + кэш + install (node/python/rust/go)
```

Поток: `push`/`pull_request` → `ci.yml` вызывает `reusable-ci.yml` с входными командами →
каждая джоба (checkout → setup → команда) отрабатывает на свежем `ubuntu-latest`.

Почему reusable + тонкая обёртка, а не один самодостаточный файл на проект (H4/H5):
канонический пайплайн определён один раз и проверен; проект декларирует только контракт.
Исправление в пайплайне распространяется копированием `reusable-ci.yml` (или pull из
харнесса), а не правкой N форков. Контракт = граница (H3): всё, что варьируется между
проектами, — входы `workflow_call`.

## Контракт `reusable-ci.yml`

| Вход | Тип | Пустое значение | Примечание |
|---|---|---|---|
| `language` | string, обязателен | — | `node` \| `python` \| `rust` \| `go`; неизвестное значение — ошибка, не дефолт (H2) |
| `node-version` / `python-version` / `go-version` / `rust-toolchain` | string | — | дефолты 20 / 3.12 / stable / stable |
| `node-cache` | string | — | `npm` \| `pnpm` \| `yarn` (флавор кэша setup-node) |
| `install-command` | string | шаг пропускается | напр. `npm ci`, `uv sync --locked` |
| `lint-command` | string | джоба пропускается | |
| `typecheck-command` | string | джоба пропускается | |
| `test-command` | string | джоба пропускается | |
| `build-command` | string | джоба пропускается | |

Правило: **пустая команда — пропущенная джоба, не ошибка**. CI отражает то, что у
проекта есть; чего нет — не выдумывается (A13).

## Порядок fail-fast (почему именно такой)

```
secret scan (gitleaks)          ← всегда, ~30–60 c [оценка], высшая тяжесть
  ├─ lint                       ← дёшево, параллельно с typecheck
  └─ typecheck
       └─ test                  ← дорого; гейтится lint + typecheck
            └─ build            ← дороже всего; гейтится test
```

Обоснование (H1): каждая минута, потраченная дорогой джобой на заведомо красный код, —
это минута, которую не потратили, если дешёвый гейт упал первым. Секреты — высшая
тяжесть (см. skill `secret-leak-guard`), поэтому secret scan стоит первым и гейтит всё
остальное. `needs` в GitHub Actions: пропущенная джоба (пустая команда) считается
успехом для зависимых — пустой `lint` не блокирует `test`.

## Модель безопасности

1. **Least privilege.** `permissions: contents: read` на уровне workflow — джобы читают
   репозиторий и ничего не пишут. Писать умеет только `GITHUB_TOKEN` gitleaks-экшена,
   и то в рамках выданных прав.
2. **CI сборки/тестов без секретов.** Канонический пайплайн не использует ни одного
   credentials: checkout работает на встроенном `GITHUB_TOKEN`, кэш — публичные registry.
   Секрет в настройках репозитория для CI — признак ошибки проектирования.
3. **Деплой/публикация — OIDC, не токены.** Когда проект дорастает до деплоя: GitHub
   OIDC provider (`aws-actions/configure-aws-credentials` с `role-to-assume` и
   `audience: sts.amazonaws.com` и т. п.) вместо долгоживущих PAT/ключей. Короткоживущий
   токен, который не нужно хранить и ротировать. Это слой, где появляются секреты, —
   и он вне универсального пайплайна.
4. **Пининг экшенов.** `actions/*@v7` (мажорный тег) — минимум. Security-sensitive
   репозитории — SHA + комментарий с версией. Запрещено: `@main`/`@master` сторонних
   экшенов (supply chain).
5. **Секреты в git — gitleaks.** `gitleaks/gitleaks-action@v3` на полной истории
   (`fetch-depth: 0`). Это эшелон поверх pre-commit-гейта харнесса: pre-commit ловит на
   машине, CI ловит то, что пришло push'ем (PR от форков, обход хуков). Ложное
   срабатывание → `.gitleaksignore` в корне репозитория, не отключение джобы.
6. **`pull_request_target` — не использовать для проверок PR-кода.** Workflow с этим
   триггером исполняется в контексте base-репозитория с секретами и доступом
   `GITHUB_TOKEN` на запись; запуск кода форка в этом контексте — классический
   «pwn request». Для проверок PR-кода — только `pull_request`. Универсальный пайплайн
   использует `pull_request` и потому безопасен для форков.
7. **Секреты в логах.** Джобы не печатают окружение (`env`, `printenv`) — правило
   skill `secret-leak-guard` действует и внутри CI. Логи CI публичны для public-репозиториев.

## Кэширование по языкам

| Язык | Что кэшируется | Ключ |
|---|---|---|
| node | `~/.npm` (или pnpm/yarn store) | `setup-node@v7` `cache:` — хэш локфайла (npm — package-lock.json) |
| python | uv cache (пакеты + venv) | `setup-uv@v10` `enable-cache` — дефолтный glob: `pyproject.toml`, `uv.lock`, requirements |
| rust | `target/` + cargo registry | `Swatinem/rust-cache@v2` — хэш Cargo.toml/lock + версия rustc |
| go | GOMODCACHE / GOCACHE | `setup-go@v7` `cache: true` (по умолчанию) — go.sum |

Правила кэша: (1) ключ обязан зависеть от локфайла — иначе кэш протухает молча;
(2) кэш — оптимизация, не корректность: `npm ci`/`uv sync --locked` обязаны давать тот же
результат при холодном кэше; (3) если прогон подозрительно зелёный — прогнать с
очищенным кэшем (A19: extraordinary claims).

## Concurrency

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Новые коммиты в ветку отменяют предыдущий прогон той же ветки: нет очереди устаревших
прогонов, минуты не сжигаются на устаревший код. Для веток-долгожителей с дорогим CI
можно ослабить до `cancel-in-progress: false` — решение за числами прогонов.

## Числа

Оценки (не измерено на этом харнессе, пометить и перемерить при первой возможности — A10):

- secret scan: ~30–60 c на историю типичного репозитория [оценка];
- lint/typecheck на node/python: ~1–2 мин без кэша, < 1 мин с тёплым кэшем [оценка];
- test: определяется проектом, это и есть главный расход минут.
- Тарификация Actions меняется; перед расчётом лимитов проверить текущие условия
  GitHub (public-репозитории бесплатны для стандартных раннеров [проверить актуально]).

Единственный честный способ — измерить собственный прогон: вкладка Actions показывает
время каждой джобы; оптимизировать только то, что измерено дорогим (A1).

## Когда расширять (и только тогда)

| Потребность | Средство | Триггер |
|---|---|---|
| Несколько версий языка/ОС | `strategy.matrix` в новой джобе | проект реально поддерживает N версий, а не «на всякий случай» |
| Покрытие | upload-artifact + сервис coverage | покрытие кто-то смотрит и на нём принимает решения |
| Security-анализ кода | CodeQL (`github/codeql-action`) | security-sensitive проект; весит минутами — осознанное решение |
| Деплой | отдельный workflow + OIDC | есть что деплоить |
| Тяжёлые сборки | self-hosted runners / larger runner | измерено: стандартный раннер не влезает по времени/ресурсам |

## Частые поломки и что с ними делать

| Симптом | Причина | Решение |
|---|---|---|
| `npm ci` падает на setup | нет package-lock.json | закоммитить локфайл; до этого — `npm install` |
| Кэш «не работает» | локфайл меняется каждый прогон | чекнуть, что локфайл стабилен (не генерится в CI) |
| Зелёный прогон без тестов | test-команда пустая или `--passWithNoTests` | добавить тесты; пустая команда = пропуск, но и гейта нет |
| gitleaks красный на мусоре | false positive | `.gitleaksignore`; если реальный секрет — ротация, а не игнор |
| Джоба вечно зелёная | `continue-on-error: true` или `\|\| true` | убрать; сбой должен быть громким (A2) |
| Секрет в логе | джоба печатает env | убрать вывод; правило secret-leak-guard действует и в CI |
| `reusable-ci.yml` пропал из проекта | случайное удаление | восстановить копией из харнесса; правки — только в `ci.yml` |

## Проверка первого прогона

1. Локально зелёные все команды из `ci.yml` (H1: CI не место первого запуска).
2. Первый прогон просмотрен джоба за джобой: порядок, кэш, времена.
3. Красную джобу чинят, а не выключают. Нет `|| true`, нет `continue-on-error`.
4. В настройках репозитория нет секретов, если нет деплоя; при деплое — только OIDC.
